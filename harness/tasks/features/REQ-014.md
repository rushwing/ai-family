## Requirement Description

Implement typed, versioned ProviderBinding contracts and pure validation in the existing `libs/state-schema` boundary, following REQ-013's strict external-input factories and detached JSON snapshots. Use the accepted canonical inventory as a read-only reference input. No new service, adapter runtime or inventory schema revision is needed for this contract slice.

### Separation and Identity

Provider mappings are a separate JSON document/collection, never fields embedded in Home, Floor, Area, Device, labels or area groups. The existing inventory schema/version, public apartment fixture, loader and resolver retain their provider-neutral behavior. Workflows and Agent plans continue to reference canonical IDs; they cannot use a provider identifier as a Device primary key.

A binding links one existing canonical Device to one provider instance and its provider-owned mapping. Canonical `home_id` and `device_id` use the REQ-013 ID vocabulary and must resolve to the supplied inventory Home and Device. Provider identifiers are opaque mapping values, not canonical IDs; never derive canonical identity from entity names, registry IDs or array positions.

Version 1 has at most one binding per canonical Device in a collection. A Device may be unbound; an empty collection is valid. This constraint is local to the submitted collection, not a claim of global uniqueness or persistent registration. Concurrent providers, migration history and persistence are deferred.

### Version-1 Envelope and Binding Fields

The separate JSON root has exactly `schema_version: 1` and `bindings` (a list). Each binding has the following required fields. Unknown envelope, binding and mapping fields are rejected; optional fields are explicit below.

| Field | Contract |
|---|---|
| `home_id` | Existing canonical Home ID, equal to the supplied inventory Home. |
| `device_id` | Existing canonical Device ID belonging to that Home. |
| `provider` | Exact project vocabulary `ha` or `mock`; case variants, unknown names and aliases are rejected. Future providers require a reviewed contract extension. |
| `provider_instance_id` | Opaque configured-instance alias matching `^[a-z][a-z0-9_-]{0,63}$` (1–64 ASCII characters), distinct from provider kind and canonical identity. Use a nonsensitive local alias, never an endpoint or credential; connection configuration is stored separately. |
| `mapping` | Provider-discriminated object as defined below. It is descriptive data only. |

Provider-specific mapping shapes:

| Provider | Mapping fields and completeness |
|---|---|
| `ha` | Required nonempty distinct `entity_ids` list of nonempty trimmed strings; optional nullable `device_registry_id` (omission normalizes to null), otherwise a nonempty trimmed string. A binding may describe one or more entities; a registry ID alone is insufficient. Entity-only mappings are supported. |
| `mock` | Required nonempty trimmed `device_key` string; no HA fields. This is a fixture identifier, not a delivered mock provider. |

These are ai-family mapping requirements, not proof that a provider resource exists. This slice performs no HA syntax/registry lookup, domain inference or capability inference. Provider-owned mapping strings are retained exactly after validation; surrounding whitespace is rejected rather than silently trimmed. Mapping strings need not match the canonical ID regex; the instance alias has the restricted vocabulary above. That vocabulary rejects URL/host-port/user-info/query/token-assignment syntax without echoing the supplied value. It cannot classify arbitrary ID-shaped text as a secret; callers must assign nonsensitive aliases rather than copy connection values. No open-ended metadata dictionary, tokens, passwords, URLs, service names, action templates, command payloads or arbitrary executable mapping expressions are accepted.

Within a collection, reject repeated canonical `device_id` values. Also reject an HA entity reused by different bindings under the same `(provider, provider_instance_id)`, or a mock `device_key` reused under the same instance. The same opaque resource identifier in distinct provider instances is allowed. HA `device_registry_id` may be shared across bindings describing disjoint entities; it is not by itself a unique resource key.

### Validation and Failure Semantics

External JSON-facing factories/validators reject unsupported versions (including booleans), missing fields, null required fields, wrong scalar/list/object types, blank or untrimmed strings, unknown structural fields, invalid provider discriminators, incomplete or mixed-provider mappings, duplicate resource members and collection collisions. Validate against the existing inventory before accepting references; reject unknown Devices, non-Device inventory IDs and cross-home references. Validation is deterministic with structured field/list-index paths and actionable reasons, consistent with REQ-013; errors must not dump full mapping documents or private values.

Return a validated typed representation and detached JSON-compatible snapshots with documented round-trip normalization. Validation reads the supplied inventory without mutating it. Provide a documented offline API for individual shape validation and collection validation against inventory; shape-only validation must not claim reference integrity. A new file loader/CLI is not required. Record the validation-library and public API choices during reviewed implementation design using existing package conventions.

### Provider Replacement Fixture

Use a fictional Device from REQ-013's public apartment inventory. Independently validate a before collection containing an HA binding and an after collection containing a mock binding for that same `(home_id, device_id)`. This is an offline fixture comparison, not a live switch, persistent update operation or provider service implementation.

Both collections validate; only provider instance and mapping data change. The complete canonical inventory snapshot remains equal before/after, including Device ID/name/area/labels and all Home/Floor/Area references. Pure room/group target resolution returns the same canonical area/device IDs. No other Device binding changes. Missing/invalid replacement data fails validation without altering the accepted input snapshot. Never generate a new Device or silently fall back to another binding or provider.

## Non-goals

Live HA calls, HA credentials/configuration/client lifecycle, discovery/import/sync and registry reconciliation (HI-S001–007/013/014); action mapping/dispatch, capability inference, authorization/confirmation implementation, task/audit execution (HI-S015/019–024); state contracts/stores; a provider interface or functioning mock provider (HI-S025–027); UI/API routes; automatic provider selection; persistent binding storage, migration history and concurrency; multi-provider bindings for one Device. A valid binding confers no permission and proves neither availability nor action support. No runtime or TC implementation is delivered by this admission.

## Acceptance Criteria

- [ ] AC1: Version-1 HA and mock bindings round-trip through strict typed contracts and detached JSON snapshots with canonical Home/Device references, provider kind/instance identity and complete provider-specific mappings; documented optional normalization is deterministic.
- [ ] AC2: Provider mappings remain in a separate collection; canonical inventory contracts, fixture schema and target resolver retain their existing behavior and reject provider fields embedded in canonical objects.
- [ ] AC3: Unsupported versions/providers, missing/blank/untrimmed values, wrong types, unknown fields, empty/duplicate entities and mixed or incomplete mapping shapes fail with deterministic field-path errors; no credentials or executable mapping fields are accepted.
- [ ] AC4: Collection validation rejects unknown/non-Device/cross-home references, duplicate Device bindings and resource collisions within an instance; unbound Devices, empty collections, entity-only HA mappings, shared registry IDs with disjoint entities and distinct-instance resource reuse succeed.
- [ ] AC5: The offline HA-to-mock replacement fixture preserves the entire canonical inventory and room/group target results, including the same Device ID and containment; invalid replacement inputs leave the accepted snapshots unchanged and never select a fallback provider.
- [ ] AC6: Contract validation and replacement verification execute without network/provider calls, HA credentials or hardware, registry lookup, state changes or action dispatch; failures do not expose complete private mapping payloads.
- [ ] AC7: Independently reviewed Harness TCs cover AC1–AC6 success/failure cases and record tested commit/environment, executed versus skipped results, applicable unit/contract/lint/type and governance checks; required runtime cases pass with zero skips before implementation acceptance.
