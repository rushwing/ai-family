## Context and bounded outcome

The shared REQ-003/004 increment supplies durable confirmation and authenticated
registration, not home policy, canonical action validity or current availability.
REQ-037 supplies semantic validation, not authentication or dispatch authority.
This slice composes those boundaries into one reusable guard, testable with
fixture policy/state authorities and real PostgreSQL, while keeping physical
execution disabled. A guard-eligible request is neither an accepted ActionTask
nor evidence that a device moved. All future physical writes still require

home.positionable/set_position actions from the accepted REQ-017 catalogue.

are necessary, never sufficient: both require explicit member/home/device/action
grants. Existing structured/read-only kid behavior and Goal tools stay intact.

## Input and configuration contract

The registered tool's business payload is exactly a raw REQ-018 ActionRequest:
schema_version, home_id, device_id, capability_id, capability_version, action_id,
arguments, idempotency_key and trace_id. No additional identity, policy, support,
availability, provider mapping or confirmation-verified field is accepted.
Transport-only prepare/confirm_token fields retain existing gateway semantics
and are removed only with confirmation_payload. Proof signing, persistence and
consumption all bind the same complete business payload, including correlation
and idempotency fields; no defaults/coercion or re-encoding into another request.
A supplied member/context field cannot override JWT identity or be silently
removed to make an invalid canonical request valid.

Trusted server configuration supplies detached inventory, exact registered
bindings, per-device descriptors, a current resource-scope authority and a clock.
No configuration/grant/lease can come from the request. One guard instance is
bound to one canonical home and selected provider-instance alias; replacement
must publish a new configuration generation, never mutate a validator in place.
The authority must prove that its leased binding/catalogue generation matches
that guard generation; missing or replaced configuration fails closed until a
matching guard is composed. No first-device, alternate instance or version fallback.

Request byte limit defaults to 65536 canonical UTF-8 bytes, exact positive int
at most 16777216, using REQ-037 structural/plain-JSON bounds. The existing HTTP
transport still has its independent 65536-byte cap. Resource-scope waits must
be finite (default 5 seconds, configurable exact integer 1–5 seconds), without
retrying confirmation consumption or business effects. Missing, malformed or
methodless runtime dependencies fail construction or return fixed unavailable;
there is no permissive lambda or in-memory confirmation fallback for home.

## Trusted identity and grants

Every external guard entry verifies the original bearer through the existing
RS256 issuer/audience/expiry verifier, requires nonblank bounded subject and
canonical family_member_id, and derives role solely from verified claims.
Reuse the gateway's sid/session_state selection and require a nonblank session
for writes. An ambiguous pair of different nonblank session claims is denied;
no request/session fallback is allowed. No new JWT algorithms or trust roots
are introduced. The tool-side AuthenticatedTool re-verifies the original JWT
at execution; trusted private guard hooks receive only its detached verified
claims, never a public arbitrary-claims argument.

Resource authorization checks exact subject/member/role plus canonical home,
device, capability revision and action against server-owned grants. Unknown or
ungranted targets yield the same forbidden outcome before any target existence,
capability or availability detail is exposed. Admin has no implicit cross-home
bypass. Allow decisions are exact booleans from validated authority data;
truthy strings or malformed policy outputs do not authorize. Grant absence or
revocation denies; an unavailable/broken authority is unavailable, never allow.

## Resource-scope consistency and final-entry protocol

A trusted resource authority supplies a bounded context-managed **scope lease**,
not a detached allow flag. The logical protocol acquires authority for the exact
verified principal and target and yields immutable grant, binding/configuration
generation and canonical state/freshness/epoch snapshots. Its final-entry form
uses the actual member-scoped PostgreSQL connection supplied by AuthenticatedTool.
The authority contract must hold protection through guard evaluation and the
internal guarded entry, then release on all success/error/timeout paths.

Use PostgreSQL row locks for mutable grants/binding versions, or an equivalent
transactional version check at the same commit boundary. Revocation/replacement
writers must participate in that exact row/version protocol. Acquire database
scope locks first, then the home/state capture barrier; release state protection
before ending the database transaction. All participating writers use the same
order; do not acquire a new grant lock while holding a store lock. Merely calling
policy twice, checking member RLS or comparing an old cached revision is insufficient.

The state authority must also fence normalized updates, disconnect invalidation,
reconciliation and configuration replacement while capturing/checking state.
Ordinary CurrentStateStore.read()/snapshot() releases its lock on return and
cannot alone satisfy a retained lease. The implementation needs an explicit
bounded capture lease or writer-coordinated version fence; it must not depend
on unsynchronized access to private store dictionaries. This is a small shared
state-store seam under this REQ, not a new durable State service. Reconciliation
must expose the same stale/generation fence to guard readers.

For distributed state/grant authorities, the injected adapter must establish an
equivalent shared fence. A process-local lock cannot certify another instance's
state. This increment must reject such unsupported composition as unavailable,
not claim multi-instance authorization consistency from the separately accepted
multi-instance confirmation store. Test adapters may use fixture PG grant rows
and a single fenced canonical store; production adapters remain deployment gates.

At the final guarded entry, recheck verified identity, exact current grants,
configuration/binding generation, canonical validity and availability on that
lease, regardless of successful preflight. A revocation/update committed before
lease acquisition is observed and denied. A participating update arriving after
acquisition waits or invalidates the version before any authorized handoff;
it cannot race through an unlocked interval. No lease or decision may escape
as a reusable permission token. The guarantee is about current committed local
observations at entry, not prediction of a physical device's future state.

## Availability rule

Require a found, initialized StateView with freshness=fresh, no stale-home or
reconnect invalidation, exact matching home/device, and availability.status=online.
Require availability ordering from the authority's current committed epoch,
non-null observed_at, and an independently fresh availability observation.
Use an injected trusted UTC clock: 0 <= now_ms - availability_observed_at_ms
<= max_availability_age_ms. The limit is mandatory server configuration, an
exact integer 1–300000 milliseconds; there is no implicit infinite/default age.
This is a conservative admission budget, not a measured production SLO.
Future timestamps, clock regression, missing epoch or uninitialized/stale state
fail closed. Validate the canonical observation timestamp before comparison.

Do not infer online status from capability metadata, a selected binding, a new
property event or an ACK. A property's recent update_at must not refresh an
old online availability observation. Recheck clock/age and the already verified JWT expiry at final entry after
lock waits; waiting for scope protection must not extend token validity. Missing bindings, offline/unknown/stale/missing observations and
reconnect invalidation all produce device_unavailable to an authorized caller;
authority/configuration failures produce guard_unavailable.

## Guard and gateway composition

The shared guard provides a non-authorizing eligibility assessment and private
preflight/final-entry hooks for the registered home tool. Eligibility result
exports exactly status (eligible/rejected/unavailable) and a finite reason
(null only on eligible). It contains no request, claims, provider identifiers,
lease/connection or credential. Repr is fixed/redacted; exports are detached.
It does not issue/consume confirmations or create tasks. It cannot be supplied
back to another entry to bypass a check.

The registered path remains the existing gateway composition:

1. Bound/parse transport; verify bearer, manifest role and session. Reject
   ordinary-channel prepare/self-confirm attempts under existing behavior.
2. Home preflight authorizes the exact target before descriptive lookups, then
   applies canonical validation and current binding/availability checks on a
   short scope lease. Invalid/denied/unavailable requests mint no confirmation
   and do not consume an existing token.
3. On the independent BFF confirmation route only, verify the exact-payload
   interaction signature and call the existing atomic PG nonce/token issuance.
   Release preflight leases before persistence; issuance confers no later grant.
4. On execution, repeat preflight, then call the existing PG token consume
   exactly once for verified member/session/home.execute_action/business payload.
   Wrong/expired/replayed tokens never reach the final guarded entry.
5. AuthenticatedTool re-verifies JWT, opens its member-scoped transaction, and
   enters the final protected guard evaluation described above. It must never
   reuse a preflight verdict as the final allow decision.
6. **Physical dispatch stays disabled.** This slice exposes no production
   executor/task sink. A valid internal assessment can be eligible, but the
   existing home execution route must return redacted 503 while the governed
   execution path is absent. Do not return a fake accepted task, physical
   success or gateway ok:true response for an unfinished write. Counted fixture
   sinks may demonstrate the guarded ordering only in integration tests.

The final-entry denial/failure can occur after token consumption; the token
remains consumed and business work rolls back, matching accepted PR #80.
Do not restore/retry tokens, auto-mint another proof or claim task idempotency.
A later admitted task/audit composition must retain the same scope protection
through recording its durable authorized intent, and revalidate at dispatch as
its owning requirements specify. It cannot treat an eligible verdict as a
persisted authorization. Failure/unknown outcome requires explicit reconciliation
and a fresh user confirmation when another attempt is appropriate.

## Ordered decisions and redacted failures

The ordered decision state machine is:

1. Transport bounds and strict structural parsing: invalid_request or
   input_too_large, with no descriptive target lookup. Identity/role/session
   checks precede all resource lookups.
2. Pre-grant: exact subject/member/role/home/device/capability/action scope.
   Unknown or ungranted home/device is forbidden (403), indistinguishable from
   a registered but ungranted target. No validator existence reason is exposed.
3. Post-grant configuration consistency: a grant claiming a home/device missing
   from the configured inventory, or a mismatched configuration generation, is
   guard_unavailable (503). REQ-037 unknown_home/unknown_device at this stage
   likewise signals configuration inconsistency; it is never a public 400.
4. Post-grant semantics: preserve REQ-037 ordering for capabilities_uninitialized,
   unknown_capability, unsupported_capability_version, read_only_capability,
   unknown_action and invalid_arguments. Then enforce the initial action
   allowlist (unsupported_action), exact bindings and current availability.
   A missing binding is device_unavailable; an inconsistent binding/generation
   is guard_unavailable.

The complete eligibility reason vocabulary is fixed below. No other REQ-037
code or raw validator exception is exposed by the guard. Shared interaction
proof/token errors belong to gateway confirmation processing, not this verdict.

| Status | Reason | Safe adapter status |
| --- | --- | --- |
| eligible | null | Internal only; no permission or ActionTask |
| rejected | unauthenticated, session_required | 401 |
| rejected | forbidden | 403; no existence distinctions |
| rejected | invalid_request, input_too_large | 400; structural only |
| rejected | capabilities_uninitialized, unknown_capability, unsupported_capability_version, read_only_capability, unknown_action, invalid_arguments, unsupported_action | 400; only after exact grant |
| rejected | device_unavailable | 409; no provider/state details |
| unavailable | guard_unavailable | 503; includes lease/clock/dependency/configuration failures |

Future-dated observation data is device_unavailable; a broken/regressing trusted
clock is guard_unavailable. unknown_home/unknown_device never appear in an
eligibility reason. Internal reasons have the above visibility; current wrapper
hooks may conservatively collapse rejected decisions to forbidden and unavailable
to home_boundary_unavailable, as specified below. TC design must assert ordering
with combined grant/configuration/semantic faults and counted zero lookups/calls.

This table is a guard-adapter contract, not an action API delivery. Existing
shared proof/token error codes and status mappings remain unchanged. Current
AuthenticatedTool hooks may conservatively collapse policy denials to forbidden
and infrastructure failures to home_boundary_unavailable; do not leak a private
exception merely to preserve a detailed code. Unexpected errors are fixed 503.
No request/JWT/proof/DSN/private household values enter logs or exception chains.
Existing transient gateway audit is not durable audit certification; HI-S023
continues to own durable append-only evidence before production writes.

### State capture lease v1 (I3)

CurrentStateStore.capture_lease(context, home_id, device_id, timeout_seconds)
is a context manager holding the existing publication lock. Its version-1
capture exposes immutable inventory, current committed epoch and a view(now_ms,
max_age_ms) read while live; all access fails after exit, and no serialization
is supported. It never reacquires the store lock. put/rebuild/apply,
mark_home_stale, advance_epoch and reconcile_home already publish under that
same lock and therefore participate without a second writer lock. Configuration
replacement must obtain the authority generation row lock before this state
barrier; guards reject generation mismatch until replaced. DB → state is the
only acquisition order. The gateway accepts only explicitly single-store-v1
authority composition bound to this store; distributed adapters are unavailable.
Authority.lease(connection, principal, target, timeout_seconds) holds PG grant
and binding/generation row protections and yields exact principal, target,
granted boolean, generation and current binding. PostgreSQL fixture adapters
implement that protocol; no production policy table/service is installed.
