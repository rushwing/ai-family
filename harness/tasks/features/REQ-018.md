### Canonical Request and Trusted Context

An Action Request requires `schema_version: 1`, `home_id`, `device_id`, `capability_id`, positive integer `capability_version`, `action_id`, object `arguments`, nonblank `idempotency_key` and nonblank `trace_id`. IDs follow existing Inventory/Capability grammars; no names, HA entities, MQTT topics or vendor operation strings serve as canonical identities. Missing/null/blank fields, booleans as versions, unsupported versions and unknown fields fail closed without coercion or generated defaults.

Request `idempotency_key` and every Request/Task/Result/evidence `task_id` or `trace_id` are exact case-sensitive ASCII tokens matching `[A-Za-z0-9._:-]{1,128}` (full string). Reject empty, whitespace anywhere, controls, non-ASCII, disallowed punctuation and length 129+; no trim, case folding or normalization is performed. Lengths 1 and 128 are valid. These tokens are caller-supplied correlation identifiers, not secrets or permission grants.

Contextual request validation requires an explicit validated inventory and Capability catalogue: the Device belongs to the stated Home; the exact capability identity/revision and declared action exist; arguments pass the actual REQ-016 action-input validator. No latest-version fallback, undeclared action, sensor write or arbitrary executable metadata is accepted. Inventory has no capability attachment contract; successful catalogue lookup does not prove the Device supports that capability. Device support/mapping resolution belongs to HI-S020/024 and the provider boundary.

Requester context is a separately supplied trusted boundary input, not a client-selectable `trusted: true` field. It requires nonblank authenticated `subject_id`, `family_member_id` and `home_id` and an exact role from the existing `admin`, `adult`, `kid` vocabulary. The context Home must equal the Request Home; all identities are retained in the admitted Task. A wire Request cannot supply or override requester, role, scope, confirmation, authorization or completion policy. Reject spoofed extra fields and missing/context mismatch. A trusted internal Task snapshot can serialize requester context for persistence, but loading it proves shape/correlation only: the trusted caller is responsible for its provenance. Pure contracts do not authenticate a token or assert membership/device authorization. Later guard/confirmation checks remain mandatory, including child restrictions.

Every request carries an idempotency key, including actions marked `safe_repeat` or `non_idempotent`; this does not change the descriptor's repeat semantics. The deduplication scope is `(home_id, family_member_id, subject_id, idempotency_key)`. A pure comparison classifies an existing Task and incoming contextual Request as distinct scope/key, same logical action, or conflicting reuse. Same action means identical canonical Home/Device/capability/revision/action plus structurally equal typed arguments, independent of object-key order; equality preserves primitive types (including integer versus float and boolean versus number) and schema-enforced integer constraints. This equality is not REQ-016 schema/enum equality: do not reuse its numeric-tolerant comparison. For a validated synthetic action with a number argument, `230` versus `230.0` under the same scope/key is conflicting reuse even though both inputs validate. Changed target/revision/action/arguments under the same scope/key conflicts. A different trace is not a new physical action: replay retains the original task_id/trace_id. No storage, allocation, locking, automatic repeat or exactly-once dispatch claim is included.

### Task, Result and Transition Semantics

A Task requires `schema_version: 1`, caller-supplied nonblank `task_id` and `trace_id`, the validated Request with trusted requester context, the selected descriptor completion policy and one exact state below. Task trace matches Request trace. Completion policy is derived from the exact selected descriptor; external callers cannot weaken it. An Action Result requires version 1, the same task_id/trace_id and canonical action identity, a matching state, and discriminated output/error/completion evidence. Contextual Result validation against a Task rejects identity, policy or correlation mismatch. Output, when present, passes the real descriptor action-output validator; valid output (including null for both initial control actions) alone is not physical completion evidence.

| State | Meaning | Permitted next states |
|---|---|---|
| `accepted` | Boundary admits a Task; dispatch and completion remain unproven. | `running`, `failed`, `timed_out`, `cancelled` |
| `running` | Caller reports execution in progress; ACK may be recorded independently. | `acknowledged`, `succeeded`, `failed`, `timed_out`, `cancelled` |
| `acknowledged` | Terminal acknowledgement outcome, allowed only for explicit `ack_only` policy; physical outcome unverified. | None |
| `succeeded` | Terminal policy evidence confirms the event or observed state criterion. | None |
| `failed` | Terminal explicit failure with a stable nonblank error code. | None |
| `timed_out` | Caller explicitly reports the completion deadline exhausted; physical outcome may be unknown. | None |
| `cancelled` | Caller reports task cancellation; this does not prove physical rollback. | None |

The pure transition helper enforces this table, policy/evidence consistency and stable identities, without dispatch, timers or mutation. A same-state exact replay is idempotent; a conflicting same-state result or any terminal-to-other-state update is rejected. Unknown states (including `completed`), backwards transitions and accepted-to-succeeded shortcuts reject. If a provider returns immediate evidence, callers explicitly record `running` before a terminal result. Nonterminal states cannot contain terminal success/error evidence. Failure/timeout/cancellation cannot include success evidence; error codes and nullable output/evidence variants are discriminated and documented. No raw provider exceptions, private arguments or credentials are included in error messages. A timed-out or cancelled Task cannot later become succeeded through this helper; later reconciliation is a separate future operation, not an automatic retry.

### Completion Evidence

Transport ACK records acceptance only. It never creates reported values, observation order/time, online availability or an event. The three existing descriptor policies are preserved with these observable outcomes:

- `ack_only`: a validated correlated ACK can end a running Task as `acknowledged`; its Result explicitly declares physical outcome unverified and cannot claim `succeeded`. This distinction keeps acknowledgement-based policy usable without presenting it as physical success. Independent requirement review must approve this vocabulary before TC design.
- `event_confirmed`: `succeeded` requires the exact declared event, payload validation through REQ-016 and trusted caller-supplied event evidence correlated to this task/trace and canonical action/device. Evidence carries caller-established generation/order and a dispatch baseline; it must belong to the current generation and be strictly after that baseline. Missing correlation, wrong event/device/task/trace, stale or wrong-generation evidence and ACKs cannot confirm. The pure helper validates supplied evidence, not its authenticity or command causation; providers must establish trusted correlation. No synthetic events are added to the initial catalogue.
- `state_converged`: derive desired targets from descriptor constants/required arguments, retaining a caller-established baseline and current epoch. Validate relevant canonical observed property values through the actual Capability property validators before using real REQ-015 State/convergence helpers. This explicitly carries REQ-017's accepted integration prerequisite: a float percentage cannot become valid merely because generic State compares numbers numerically. Success requires `confirmed`: current-epoch online availability and every target known, matching and strictly post-baseline. Missing/null/cross-epoch baseline, unknown/offline availability, absent/unknown properties, stale/wrong-generation reports and mismatches cannot succeed. Preserve legitimate false/zero and do not fabricate observations. Observed agreement does not prove the command caused the change.

Completion evidence and typed output are separate. Valid output or an ACK cannot replace required event/State evidence. A supplied `succeeded` state must undergo contextual evidence validation; shape-only deserialization must be named/documented as such and cannot be presented as trusted completion. No public contextual completion validator accepts an unsupported success claim.

### Offline Examples and Failure Semantics

Future tests use the packaged Switchable `set_on` and Positionable `set_position`, fictional inventory and explicit trusted context. Event-confirmed and ack-only tests use small validated synthetic descriptors without changing the six initial definitions. Representative cases:

| Input or evidence | Expected outcome |
|---|---|
| Canonical Switchable request with `{"is_on":false}` and complete trusted context | Valid contextual Request; explicit accepted Task retains false and all correlation identities. |
| Missing Device/capability/action, unknown revision, `{"is_on":0}`, extra argument, or Positionable float/out-of-range input | Reject before a Task can be admitted by the contextual validator. |
| Client `requester`, `role`, `trusted`, confirmation or completion-policy override; mismatched context Home | Reject without claiming authentication/authorization. |
| Same scoped key/typed payload with new trace | Same logical action; original Task/trace preserved. |
| Same scoped key with changed target or typed argument | Conflicting reuse; no inferred retry. |
| Both initial action outputs validate as null; only ACK follows | Task cannot succeed and State remains unconfirmed. |
| Known matching false/zero targets, current online epoch, all reports strictly after baseline | State-converged Task can succeed through actual Capability and State validation. |
| Correlated declared post-baseline current-generation event | Event-confirmed Task can succeed; wrong identity/event/order rejects. |
| Explicit ack-only descriptor with correlated ACK | Terminal acknowledged Result with physical outcome unverified; succeeded rejects. |
| Invalid state, terminal regression, wrong task/trace, or success/error mixed variant | Reject deterministically without mutating input. |
