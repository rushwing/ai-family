## Requirement Description

### Package and Integration Boundary

Extend `toolsets/iot/home-device-fabric` within its existing distribution. Package the scenario builders, caller integration and public fictional fixtures so the CLI runs from installed wheels outside the checkout. Reuse shared validators and the existing `MockProvider`; do not copy Task transitions, State ordering, capability validation or provider deadline logic. Runtime code must not import `tests`, run test scripts or depend on repository-relative paths. Freeze Python exports and exact JSON envelopes/error vocabulary during reviewed TC design before implementation. Compatible state-schema and fabric distributions continue to be installed together.

The CLI provides a synchronous offline caller: discover devices/bindings/support, obtain snapshots, construct and validate requests/Tasks using explicit fictional caller context, submit eligible running Tasks, consume virtual-time deliveries in order, apply normalized inputs through State helpers, validate Result/evidence and transition/settle Tasks through Action helpers. Caller context is demonstration data, not authenticated permission. Record every dispatch, input and outcome needed to inspect that flow, with canonical IDs and exact capability revisions. Rejected requests have zero provider dispatches.

### Device Scenario Models

| Device | Existing exact capability | Required behavior |
|---|---|---|
| MockSwitch | `home.switchable` revision 1 | `set_on` accepts only boolean `is_on`; explicit scripted on/off reports update State, including false. ACK leaves the Task running until eligible matching evidence arrives. |
| MockCurtain | `home.positionable` revision 1 | `set_position` accepts strict integer `position_percent` in inclusive 0–100. Script initial, intermediate and final positions at declared virtual times; intermediate values do not complete a different target. No rounding, interpolation or inferred progress. |
| MockTemperatureSensor | `home.temperature_sensor` revision 1 | Publish explicitly scripted finite `temperature_c` observations in Celsius, including zero and negative valid values. No action exists; attempts to write temperature reject before dispatch. |

Each model builds explicit validated registrations and scenario data for the existing provider. A future report is supplied independently in the selected fixture, never computed from submitted action arguments. At least one scenario deliberately reports a value different from the requested target, proving that intent does not manufacture completion. Fresh instances start unknown until scripted initial observations/availability arrive; offline availability remains separate from last known values and does not turn them into false/zero. Fictional canonical IDs and mock-instance bindings are stable across repeat runs.

### State-change Timeline and Curtain Motion

The admitted candidate asks for a canonical switch event and curtain motion/completion. Existing revision-1 descriptors have empty `events`; preserve those descriptors and revisions. Here the switch emits a CLI state-change timeline record containing the actual validated canonical property input and resulting State. This is a caller-side record of a simulated state update, not a new Capability event or a production bus publication. Curtain motion is an ordered sequence of explicit position observations in the same timeline; any displayed moving/complete label is demo metadata, not an added canonical property or measured physical claim. Final matching State supplies completion evidence under the existing `state_converged` policy. A first-class Capability motion/state event would require separately reviewed versioned schema work. Requirement review must explicitly settle this bounded interpretation of the candidate.

### CLI Contract

Expose `python -m home_device_fabric.demo` after package installation. The commands below are implemented by the packaged offline demo; external acceptance remains pending:

```bash
python -m home_device_fabric.demo --device switch --scenario success
python -m home_device_fabric.demo --device curtain --scenario success
python -m home_device_fabric.demo --device temperature --scenario observe
python -m home_device_fabric.demo --device switch --scenario timeout
python -m home_device_fabric.demo --device switch --scenario offline
python -m home_device_fabric.demo --device curtain --scenario invalid-position
python -m home_device_fabric.demo --device temperature --scenario write-rejected
```

Each invocation runs one complete named, packaged scenario in a fresh process with explicit virtual time; no service, token, network, wall-clock sleep or environment configuration is needed. Standard output contains exactly one versioned JSON object identifying simulation, device/scenario, discovered registration, validated capability metadata (including temperature units), initial/final State, ordered timeline with virtual times, Task/result when applicable, typed rejection when applicable and dispatch count. Sensor observation has no invented action Task. The precise schema and strict JSON text comparison are frozen in [demo API contract](../evidence/REQ-020-api-contract.md). Serialize with json.dumps(sort_keys=True, separators=(",", ":"), allow_nan=False) plus one newline; compare complete stdout text, preserving numeric and boolean types and list order. JSON uses finite values and type-sensitive deterministic serialization; exclude ambient timestamps, paths and generated identifiers. Expected negative scenarios retain state/Task/error evidence in JSON.

Exit 0 means the scenario executed and all its declared expectations hold, including expected timeout/offline/rejection. Exit 1 means an internal execution or scenario expectation failed. Exit 2 means unsupported CLI arguments or an unknown device/scenario combination; write value-free diagnostics to stderr. Assertions must remain effective under optimized Python. The documentation distinguishes scenario-verification success from a device action succeeding, and includes JSON examples and a small assertion command users can run without pytest.

### Required Scenarios and Completion Rules

Switch success covers both boolean targets; curtain success covers endpoints 0/100 and an intermediate target with explicit movement observations. Temperature observation covers finite zero/negative/positive samples and Celsius metadata. ACK-only with no matching evidence reaches the descriptor deadline and yields timed_out with unverified physical outcome. Offline scenarios for all three devices preserve availability/unknown-versus-known semantics; action scenarios cannot confirm completion from offline evidence. The demo checks reported availability before a new dispatch and rejects an already-offline device with zero dispatches; this is a demo/caller policy, not production authorization. It does not change the frozen REQ-019 MockProvider.submit semantics; moving it into the provider requires separately reviewed provider-contract work.

Curtain invalid-position includes -1, 101, fractional values and bool; sensor write attempts and malformed switch arguments reject through real shared validation before dispatch. Additional action cases cover mismatched reported target, stale/wrong-epoch evidence, exact deadline ties and late observations after timeout. Use existing timeout values (switch 30,000 ms; curtain 120,000 ms), chronological delivery, timeout-wins-ties and explicit settlement rules. Repeated virtual advancement never repeats delivery and terminal Tasks never change. Advancing once beyond both pre-deadline evidence and deadline must still allow eligible earlier evidence to complete. A valid successful action dispatches exactly once; no retry or second effect is implicit.

## Non-goals

The CLI's confirmed outcome describes simulated evidence only.
