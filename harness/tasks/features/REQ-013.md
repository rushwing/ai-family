# REQ-013 — Canonical Home Inventory Contracts

## Background

human-001 explicitly requested admitting HI-S008 to Harness on 2026-10-08, with Home -> Floor -> Area -> Device containment, room types, names, labels, seven room-group presets and an editable three-bedroom apartment. This expands the original Home/Area/Device slice to include Floor and inventory/target selection contracts. This file is the sole editable implementation specification for HI-S008. The product Story is a navigation record.

## Requirement Description

Implement typed contracts, inventory loading/validation and pure target resolution in the existing shared `libs/state-schema` boundary. Use existing repository/package conventions; select the validation library during reviewed implementation design. Inventory is versioned JSON, independent of HA credentials and registry IDs. The public example is a fictional design fixture, not a declaration of human-001's actual home or an HA-native configuration file.

### Naming and Home Assistant Alignment

Use snake_case field names and machine vocabulary IDs, with editable human-readable `name` values. HA's area registry uses `id`, `name`, `aliases`, `floor_id` and `labels`; labels reference registry IDs. HA floors have a numeric `level`, including negatives; devices belong to an area rather than directly to a floor. Adopt those concepts, keeping canonical IDs separate from provider IDs.

`home_id`, `residence_type`, `area_type`, inventory schema and `area_groups` are ai-family extensions, not HA registry fields or HA Scenes. Do not represent these group presets as HA category IDs, automations, executable workflows or permissions. Actual HA registry IDs/entity IDs are future ProviderBinding/adapter data (HI-S009/014).

Sources checked on 2026-10-08:
- [HA Area registry](https://developers.home-assistant.io/docs/area_registry_index/)
- [HA Floors](https://www.home-assistant.io/docs/organizing/floors/)
- [HA Labels](https://www.home-assistant.io/docs/organizing/labels/)

### Inventory Envelope and Objects

The JSON root contains `schema_version: 1`, `home`, `floors`, `areas`, `devices`, `labels` and `area_groups`. Reject unsupported versions and unknown structural fields with a field path; keep optional fields explicit. Do not silently coerce IDs, numbers or spelling mistakes.

| Object | Fields and semantics |
|---|---|
| Home | `id`, `name`, `residence_type`; permitted residence types: `apartment`, `detached_house`, `townhouse`, `duplex`, `other`. |
| Floor | `id`, `home_id`, `name`, integer `level`, optional `aliases` (default `[]`). Basement = -1, Ground Floor = 0, Upper Floor = 1 are suggested names/levels, not mandatory IDs or limits. Reject booleans as levels. |
| Area | `id`, `home_id`, `area_type`, `name`, nullable `floor_id`, `labels` (default `[]`), optional `aliases` (default `[]`). One area has at most one floor; null supports unassigned/outdoor areas. |
| Device | `id`, `home_id`, `name`, nullable `area_id`, `labels` (default `[]`). Floor is derived through the area. Null supports unassigned devices. No mandatory HA `entity_id`, provider identity or capability/state payload. |
| Label | `id`, `name`; inventory-local reusable classification. Area/Device `labels` contain distinct registered label IDs, not display names. |
| Area group | `id`, `name`, nonempty distinct `area_types`; a configurable union of room types, scoped to this Home. Selection is a pure query. |

Canonical object IDs are immutable after creation, unique across Home/Floor/Area/Device/Label/Area-group records in one inventory, nonempty and match `^[a-z][a-z0-9_-]{0,63}$`. Both `area-bedroom-02` and snake_case IDs are valid. Never regenerate IDs from mutable names, array positions, floor levels or provider identities. Names are nonempty trimmed strings; aliases are distinct nonempty strings. Duplicate display names are permitted; references and target selection use IDs. Renaming or moving an existing object preserves its ID.

All Floor/Area/Device `home_id` references must match the inventory Home. An Area's floor, if assigned, must exist in the same Home. A Device's area, if assigned, must exist in the same Home. Reject dangling and cross-home references, duplicate IDs/labels, wrong scalar/list types and unknown label IDs. Provider replacement must not change the canonical Device contract.

### Area Types and Room-group Presets

`area_type` is a snake_case classification separate from `name`. The initial supported room types and suggested groups are below; `other` supports a room outside these presets. Additional snake_case types may be configured by extending the reviewed vocabulary in a future schema revision; arbitrary typos are rejected in version 1.

| Preset ID / name | Area types |
|---|---|
| `daily_life` / Daily Life | `living_room`, `dining_room` |
| `resting` / Resting | `bedroom` |
| `kitchen_bath` / Kitchen & Bath | `kitchen`, `bathroom`, `laundry_room` |
| `studio` / Studio | `study`, `home_office`, `playroom` |
| `traffic` / Traffic | `entrance`, `hallway`, `stairwell` |
| `storage_utility` / Storage & Utility Spaces | `storage_room`, `garage` |
| `outdoor_spaces` / Outdoor | `balcony`, `terrace`, `garden` |

Groups are editable inventory data: users can rename, add or remove groups and change their area-type members within the supported vocabulary. An unused group is valid and resolves to an empty result rather than inventing areas. Initial labels include `primary`, `guest`, `children`, `outdoor` and `elderly`; users may add registered labels. Correct the supplied `childen` typo to `children` in the example; runtime validation rejects undeclared spellings rather than inferring intent. Labels convey classification only; they do not grant permissions or prove a person's age/identity.

### Target Resolution Contract

Provide a pure resolver accepting `home_id` and a selector containing exactly one of nonempty distinct `area_ids` or nonempty distinct `area_group_ids`, plus optional distinct registered `label_ids`. Explicit area IDs are selected directly; groups select the union of areas whose `area_type` is a group member. When `label_ids` is present, an area must contain all requested labels (intersection). Return sorted unique `area_ids` and sorted unique `device_ids` assigned to those areas, with no dispatch or provider call. Device labels do not implicitly broaden area selection. An empty resolved set is a valid explicit result.

Reject wrong Home, unknown area/group/label IDs, both selector forms, no selector, empty selector lists and duplicate selector IDs. Never fall back from an invalid/empty selection to the whole Home. Subsequent HI-S019/020/022/029 work must apply capability, identity, member/device scope and confirmation checks before using these resolved targets for actions.

### Editable Apartment Fixture

[three-bedroom-apartment.example.json](../../../docs/product/home-intelligence/examples/three-bedroom-apartment.example.json) provides one fictional apartment Home, one Ground Floor (level 0), three bedrooms named Master Bedroom, Daughter's Room and Elderly Bedroom, plus Living Room, Dining Room, Kitchen, Bathroom, Laundry Room, Entrance, Hallway and Balcony. Three fictional bedroom lights demonstrate Device containment; no credentials, actual inventory or provider bindings are supplied. All seven presets exist, including empty studio/storage selections.

[Example instructions](../../../docs/product/home-intelligence/examples/README.md) explain copying to a Git-ignored `*.home-inventory.local.json`, editing names/levels/types/labels/device assignments while retaining stable IDs, and using area/group/label selectors. During implementation provide a documented loader/validation command that accepts an explicit file path, reads UTF-8 JSON, returns actionable errors and makes no network calls. The public example is a specification fixture until the loader and resolver pass their Harness TC; documentation must not imply they already exist.

No backend implementation is delivered by the admission PR. No bulk Story promotion or change to the thirty-Story R1 boundary.

## Acceptance Criteria

- [ ] AC1: Home/Floor/Area/Device and inventory label/group contracts round-trip valid version-1 JSON, with stable IDs and HA-aligned area/floor/label field names; provider replacement does not alter canonical Device fields.
- [ ] AC2: Basement -1, Ground Floor 0 and Upper Floor 1 are accepted; editable residence types, room types, names and labels remain independent; renaming/moving retains IDs and existing references.
- [ ] AC3: Missing/invalid IDs, duplicates, blank names, unknown fields/types/version/labels, dangling references and cross-home containment fail with deterministic field-path errors. Nullable unassigned area/floor relationships succeed.
- [ ] AC4: The fictional editable apartment fixture validates with exactly three bedroom areas (master/daughter/elderly), correctly assigned devices, all seven group presets and registered `children` labels; private edits stay outside tracked artifacts.
- [ ] AC5: Explicit area, group-union and optional all-label filtering return sorted deduplicated area/device IDs; Resting selects three bedrooms, Resting + children selects only Daughter's Room, and unused groups resolve empty. Wrong Home/unknown targets/ambiguous or empty selectors fail without whole-home fallback.
- [ ] AC6: The documented offline loader validates both the public fixture and a renamed/moved private copy; it emits useful errors for malformed JSON and unsupported versions, without provider/network calls or device writes.
- [ ] AC7: Harness TC records commit/environment evidence for all success and failure cases; required unit/contract checks, applicable lint/type checks and governance gates pass before implementation review. Engineering completion derives only from this REQ.
