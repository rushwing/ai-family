## Requirement Description

After independent requirement approval and required Harness TC gates, add the shared provider records/validation to `libs/state-schema` and the provider protocol/mock implementation to `toolsets/iot/home-device-fabric`, following ADR-016 and architecture alignment. Implement only necessary modules and packaging; preserve shared contracts as the single source of canonical validation. Freeze exact public imports, method signatures, envelopes, error codes and packaging commands during reviewed TC design before implementation. Internal Python calls are the offline testing seam; they do not replace the production RabbitMQ task boundary.

### Typed Provider Boundary

The interface identifies a provider kind and canonical provider-instance alias using REQ-014 semantics, and covers these independently usable operations:

| Operation | Required behavior |
|---|---|
| Discovery | Return explicitly configured device registrations, validated separate bindings and exact supported capability identity/revision pairs; preserve canonical IDs. |
| Current snapshot | Return validated canonical reported observations and availability with provenance/order metadata, detached from provider internals. |
| Normalized input delivery | Expose state/availability updates and declared capability events, with canonical identity and explicit ordering; delivery alone does not mutate a shared Home State Store. |
| Action submission | Accept an internal validated Task and explicit selected binding/support context; return correlated acknowledgement or structured failure and schedule simulated outcomes. |
| Outcome delivery | Expose correlated output/error/evidence for an explicitly supplied virtual time; completion is adjudicated through actual REQ-018 helpers. |

Define typed records or a Protocol with typed records, not an untyped arbitrary-operation callback. Version every new externally serialized envelope with integer `schema_version: 1`, rejecting booleans, unknown fields/versions, malformed values and non-JSON/cyclic/nonfinite input. Records and returned snapshots must not retain mutable caller references. Errors expose fixed typed reasons and safe field locations without input values, credentials, endpoints or exception chains. Do not weaken accepted shared validators or add ambient inventory/catalogue/provider lookup.

### Explicit Discovery and Support

Mock configuration supplies one validated Home inventory, separate REQ-014 bindings, a validated Capability catalogue and explicit per-device supported identity/revision pairs. Discovery reads this configuration only; it does not scan a network, assign canonical IDs, infer a capability from a name, or attach provider data to Inventory. Bindings must reference this Home/Device, have provider `mock`, belong to this mock instance and obey existing resource uniqueness. Unknown devices, duplicate support pairs, undeclared catalogue revisions and foreign-instance bindings reject at configuration admission. A supported read-only descriptor may be discovered but has no executable actions.

Keep `device_key` and any provider-specific operation identifiers in binding/provider data. Northbound Action Requests, Task identity and completion evidence keep canonical IDs; they acquire no vendor-operation fields. The support table is trusted mock configuration, not a caller-writable permission grant or a generic production capability-attachment registry. HI-S015/020 retain production mapping/resolution work.

### Normalized Observations and Events

State snapshots/updates reuse REQ-015 identity, reported/desired separation, availability, timestamps and Ordering. Every known property value passes the actual validator for its explicitly supported capability revision before State application or completion evaluation. Reject ambiguous property ownership in a mock device's support configuration rather than guessing between descriptors with the same property name. Missing/unknown/offline remains explicit; never substitute false, zero or desired intent for an observation. Preserve legitimate false/zero and reject fractional canonical integer positions.

Every delivered item identifies this provider instance and canonical Home/Device; property updates additionally identify capability/revision/property, and capability events identify capability/revision/event with schema-validated payload and explicit Ordering. The shared protocol can carry a declared event from an injected valid catalogue. The initial REQ-017 catalogue has empty event sets: do not invent switch/motion/availability capability events. State and availability updates are distinct normalized transport items, not fabricated descriptor events. Correlation to an action is explicit and cannot be inferred solely from the device ID or matching value.

Use actual REQ-015 update/order rules at the caller integration seam. Stale, duplicate and wrong-epoch observations cannot overwrite newer current observations or establish completion. Snapshot access never creates freshness or a new sequence. A scenario may deliberately deliver stale/out-of-order observations for negative tests; it must not bypass canonical shape/payload validation.

### Internal Action Submission and Completion

Action submission revalidates the Task against explicit inventory/catalogue, selected mock binding and configured support. Only a `running` Task with its existing frozen dispatch context is eligible. The offline harness creates accepted Tasks and transitions them to running through real REQ-018 helpers before submission. Missing support, unknown device/action/revision, invalid typed arguments, binding mismatch or invalid Task rejects before any scheduled effect; expose structured errors and an inspectable dispatch/effect log for zero-effect assertions. Do not add a public route, auto-create running Tasks or treat shape validation as authentication/confirmation.

The mock is an internal simulator behind the future guarded task path. Its caller must eventually enforce trusted identity, member/device scope, risk, confirmation and durable audit before production dispatch. This slice supplies no authorization verdict, confirmation token, bypass flag or deployable physical executor. Mock instance isolation and explicit binding/support checks are contract integrity, not substitutes for policy.

Retain Task identity, exact selected completion policy and original task_id/trace_id in every outcome. Provider ACK and valid null output remain distinct from observed completion. For `state_converged`, feed independently scripted reported observations through actual Capability/State validators and REQ-018 Result/transition helpers; success requires eligible current-epoch online post-baseline evidence matching all requested targets. ACK alone leaves the Task running. For `ack_only`, REQ-018 permits acknowledged, not confirmed success. Declared `event_confirmed` evidence follows REQ-018 event schema/order/correlation rules; a fictional descriptor may exercise the generic interface without extending the initial catalogue.

Do not manufacture an observation from submitted arguments. A test scenario explicitly supplies each future observation and its virtual delivery time; the mock can publish that declared simulated observation, but reports no measured physical effect or causation. An ACK at the deadline cannot establish physical completion. Timeout/failure/cancellation preserve REQ-018's unverified physical outcome; malformed or mismatched provider outcomes never become success.

### Deterministic Time and Failure Scenarios

The mock uses a caller-controlled virtual monotonic time in nonnegative integer milliseconds and explicit UTC timestamps/epoch/sequence for observation provenance. No wall-clock reads, sleeps, timers, environment variables or random generation determine behavior. Virtual time cannot move backwards. Due items are delivered in increasing due-time order, then configuration insertion order for ties; consuming delivery returns each scheduled item once in that mock instance. Snapshot and discovery are non-consuming detached reads. Fresh instances with identical fixtures and the same input/time sequence produce structurally and type-identically equal outputs/logs.

Scenario configuration supplies relative delivery delays and validated outcomes for each explicitly identified submission attempt. Malformed scenarios reject before use. Submission time is the caller's virtual dispatch time; the exact selected descriptor `timeout_ms` sets the deadline. At `now >= deadline`, timeout wins over completion evidence scheduled at the same instant; confirmation requires evidence delivered before the deadline. Freeze this tie rule in TCs. Timeout is produced at explicit time advancement/polling, never by an implicit worker. Delayed evidence may still be delivered as an observation after timeout but cannot change a terminal Task or trigger another effect.

Required scenarios cover ACK then eligible convergence, ACK with no observation until deadline, dispatch rejection before effects, failure after ACK with uncertain outcome, offline/unknown state, stale/wrong-epoch evidence and late evidence after timeout. Cancellation suppresses still-pending scripted action outcomes for that attempt and retains the Task's existing cancellation semantics. It does not retract already delivered observations, remove independent state/availability inputs or promise physical undo. No persistence/restart recovery, device motion interpolation or automatic retries are added.

Caller-controlled retry tests explicitly supply another attempt and script; the mock records attempts and never retries on its own. Reuse real REQ-018 idempotency comparison to demonstrate scoped replay/conflict at the caller seam, retaining original task/trace on replay and making zero further provider submissions. The provider itself does not claim durable deduplication, exactly-once execution or that safe-repeat metadata authorizes retry. Non-idempotent/uncertain attempts receive no inferred retry permission. Per-instance scripted attempts/logs are test instrumentation only.

## Non-goals

Live HA/MQTT/Matter/vendor adapters or credentials; network or device writes; REST/MCP endpoints; production Task Service, State Store, queues, database, guard, audit or confirmation; general provider-operation resolver or HA mapper; durable idempotency/retry/restart guarantees; HI-S026 switch/curtain/sensor behavior models and motion events; HI-S027 full adapter conformance; R2 workflows; UI changes; new capabilities, implicit observations, catalogue events or weakened child restrictions. These require their own admitted requirements.

## Acceptance Criteria

- [ ] AC1: A typed versioned provider interface covers discovery, snapshots, normalized state/availability/events, action submission and correlated outcomes; strict admission rejects malformed configuration/envelopes and snapshots remain detached.
- [ ] AC2: Discovery preserves canonical Home/Device identity and separate bindings, exposes exact explicitly supported revisions and rejects cross-Home/instance/unknown/duplicate registrations without provider lookup.
- [ ] AC3: Known values and declared events pass actual Capability validators before actual State/order integration; unknown/offline/false/zero retain their meanings and stale/wrong-epoch evidence cannot establish freshness or completion.
- [ ] AC4: Only an eligible running Task with a matching binding and supported exact action can submit; every invalid target/support/argument/context case returns a typed reason with zero scheduled effects or dispatch-log entries.
- [ ] AC5: An offline discovery → snapshot → accepted/running Task → ACK → explicitly scripted post-baseline observation → Result/transition scenario demonstrates confirmed simulated convergence through real REQ-015/016/018 helpers; ACK-only, invalid/mismatched/stale/late evidence cannot succeed.
- [ ] AC6: Injected virtual time deterministically reproduces successful, rejected, failed, offline, cancelled and timed-out scenarios, including exact deadline ties and late observations; terminal Tasks stay terminal and advancing time never repeats delivery/effects.
- [ ] AC7: Explicit caller retry and scoped replay/conflict checks preserve original task/trace and prove no automatic retry or second dispatch on replay/conflict; neither logs nor metadata are represented as durable deduplication or production permission.
- [ ] AC8: Network-disabled required-mode TCs execute with zero skips, deny ambient I/O/time/random dependence, exercise mutable-input/result isolation and value-free errors, and installed-artifact smoke validates shared contracts plus provider/mock imports outside the source checkout.
