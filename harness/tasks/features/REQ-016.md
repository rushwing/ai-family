### Version, Identity and Collection

The exact collection envelope is `{schema_version: 1, capabilities: [...]}`. Each descriptor has exactly `schema_version`, `capability_id`, `capability_version`, `title`, `description`, `properties`, `actions` and `events`; all are required. `schema_version` is the integer 1. `capability_version` is a positive integer revision of one stable capability identity, independent of the envelope schema. Booleans, coercible strings, floats and unsupported schema versions reject. Version 1 of the validator accepts any positive capability revision structurally; selecting a supported `(capability_id, capability_version)` requires an exact match in the supplied catalogue, never a fallback to latest. Validation alone does not certify compatibility with a consumer.

`capability_id` matches `^[a-z][a-z0-9_]{0,31}(\.[a-z][a-z0-9_]{0,31}){1,3}$` (for example `demo.power`). It is a stable capability type identity, not a Device ID, HA entity, service name, endpoint or credential. The collection rejects duplicate identity/revision pairs; multiple revisions of an identity may coexist. Empty collections are valid. Descriptor revision changes whenever the machine contract changes; older revisions remain addressable. This slice supplies no migration, semantic compatibility inference or default-version resolution.

`title` is a nonblank string of at most 256 characters; `description` is a nonblank string of at most 2048 characters. Human text cannot grant actions or override machine metadata. `properties`, `actions` and `events` are objects keyed by canonical member names matching REQ-015's `^[a-z][a-z0-9_]{0,63}$`. Names are unique within each map (JSON loaders must reject duplicate object keys before dict validation); separate interaction maps may reuse a name because interaction kind is explicit. Empty maps and sensor-only descriptors with no actions are valid. At least one interaction across the three maps is required for a descriptor. Unknown interaction names or versions fail closed during payload validation. Attaching capabilities to Devices, inventory extensions, provider translation and catalogue persistence are later work.

### Properties, Actions and Events

| Interaction | Exact required fields | Meaning |
|---|---|---|
| Property | `title`, `description`, `value_schema`, `read_only` | Named canonical reported value; `read_only` is a strict boolean. Its schema type is boolean, integer, number or string to match REQ-015 State scalars. |
| Action | `title`, `description`, `input_schema`, `output_schema`, `risk`, `timeout_ms`, `idempotency`, `completion_policy` | Named typed intent with explicit execution metadata; both schemas are mandatory, including parameterless/no-result actions. |
| Event | `title`, `description`, `data_schema` | Named observation/event payload contract, without subscription addresses or runtime delivery promises. |

Interaction text obeys the descriptor text limits. Every record rejects unknown and missing fields. Property absence/unknown/offline is represented by REQ-015 State metadata outside `value_schema`; it is never encoded as an off/zero default. A writable property is only descriptive and grants no write endpoint. Writes must be represented by a declared action and pass future authorization/confirmation. `read_only: true` prevents state-converged targets from writing that property, but does not prevent events/actions observing it. This contract does not implement writes to any property.

Action input uses an object schema, including `{type: "object", properties: {}, required: [], additionalProperties: false}` for no arguments. Action output and event data may use any supported schema type. `{type: "null"}` explicitly denotes no result. Output validates provider/task result payload shape; even an output containing `accepted: true` is not an observation or physical completion. Input/output/event/property values are validated through pure explicit descriptor/version/member selection; validation cannot execute an action, publish an event or update State.

### Bounded Embedded Schema Profile

Use an explicitly restricted JSON Schema-style profile, not a claim of complete WoT Thing Description or JSON Schema conformance. This project profile has no implicit keyword defaults. The future validator validates schema structure as well as instance payloads. All schema nodes require a single string `type` from `boolean`, `integer`, `number`, `string`, `null`, `object`, `array`. No type arrays, coercion or Python-only objects are accepted. Numbers are finite; integer excludes booleans and floating values. Number accepts finite integer/float values but excludes booleans. Null accepts only null. Payloads and schema constants must be strict JSON, including nested values, finite numbers and string-keyed objects.

Supported optional keywords are `enum` for scalar types, inclusive `minimum`/`maximum` for integer/number, and nonnegative integer `minLength`/`maxLength` for string. `enum` is nonempty, has distinct type-correct values, and every value satisfies the node's other constraints. Boolean/number equality is type-sensitive; numbers compare numerically, so 0 and 0.0 are duplicate number enum members. Bounds must be finite, have the node's numeric type (integer bounds are integers), and minimum must not exceed maximum; minLength must not exceed maxLength. Missing optional bounds mean unbounded, never a synthesized instance value.

Object schemas require exactly `type`, `properties`, `required`, `additionalProperties` plus no other keywords. `properties` maps canonical member names to schemas; `required` is a list of distinct declared names and may be empty; `additionalProperties` must be literal false. Optional properties may be omitted but are never populated with defaults. Undeclared payload keys reject. Array schemas require `type` and one schema-valued `items`; optional `minItems`/`maxItems` are nonnegative integers with ordered bounds. No tuple items. Scalar nodes accept only the applicable keywords above, and null nodes only `type` and an optional enum containing null.

Reject `$ref`, `$id`, `$schema`, remote/local resolution, `default`, `format`, `pattern`, composition (`allOf`/`anyOf`/`oneOf`/`not`), executable validators and any unlisted keyword. No network/schema registry fetch is allowed. Schema or payload nesting beyond 16 nodes on a root-to-leaf path rejects, with the root at depth 1; recursive/cyclic Python inputs reject deterministically. This bounded profile supports later initial schemas without importing ontology or vendor runtimes. Units, tolerances, specialised six-capability definitions and expanding the keyword profile require their own reviewed contract changes (HI-S012); no undeclared semantics are silently ignored.

### Action Execution Metadata

All four fields are mandatory for every action; no missing risk, timeout or completion default is safe.

| Field | Version-1 values and constraints |
|---|---|
| `risk` | Exact enum `low`, `medium`, `high`. Unknown/missing risk rejects. This is a descriptor declaration, not authorization. Future policy may raise risk or deny; it cannot use this metadata to bypass trusted scope/role checks, confirmation or disabled high-risk actions. Mapping to gateway policy is deferred. |
| `timeout_ms` | Integer 1–86400000 inclusive, excluding booleans; milliseconds for the future task's completion deadline starting when governed dispatch begins. Queue/admission timeout is separate. Invalid/zero/negative/oversized values reject; no clock/timer runs here. Expiry means completion was not established in time, not proof the action failed physically or rollback succeeded. |
| `idempotency` | Exact enum `safe_repeat`, `key_required`, `non_idempotent`. Safe repeat declares repeating the same intent has the same intended effect; key required requires future durable deduplication by request key; non-idempotent forbids automatic replay/retry of an ambiguously accepted action. No enum is proof of a provider guarantee and none permits bypassing task-level identity/audit. Deduplication, key scope/retention and retry execution belong to HI-S019 and later runtime work. |
| `completion_policy` | Required tagged object specified below; missing or unknown kind rejects. A descriptor states evidence requirements; it does not implement a task state machine or certify completion. |

### Completion Policies and Evidence Boundary

`completion_policy` has exactly one of the following shapes; keys from other kinds reject.

- `{kind: "ack_only"}`: future task success means the provider accepted the request. Queue receipt, internal admission or transport receipt alone is insufficient unless the later provider contract explicitly defines it as provider acceptance. Task success under this policy makes no physical-convergence claim and cannot fabricate reported values, online availability, observed_at or ordering.
- `{kind: "event_confirmed", event: "<declared event name>"}`: the referenced event must exist in this descriptor. The future task requires a schema-valid event causally correlated to this invocation and received within its completion deadline. An unrelated, stale, retained or uncorrelated event is insufficient. Correlation/request envelope and terminal success/failure semantics must be defined in reviewed HI-S019/adapter contracts before execution; this base descriptor supplies no implementation or invented correlation IDs. Event-confirmed task completion does not independently prove all desired State values converged.
- `{kind: "state_converged", targets: {"<property>": <target source>, ...}}`: targets is nonempty; each key names a declared writable property. A target source is exactly `{source: "input", field: "<top-level required input field>"}` or `{source: "constant", value: <scalar>}`. Input sources must reference a required scalar input field whose entire schema node equals the target property schema (conservative v1 compatibility rule); no nested paths, transforms, inferred conversions or optional source fields. Constant targets must validate against that property schema. Unknown/read-only properties, malformed sources, incompatible schemas and extra keys reject. Targets supply future desired values, not reports. Units/conversion/tolerance and complex comparison policies are excluded.

The future state-converged task must use REQ-015 semantics: current-epoch online availability, known current-epoch reports for every desired target, strict report ordering after the intent baseline, and type-sensitive value agreement. Null/cross-epoch baseline, offline/unknown/missing observations and old matching values cannot confirm. Current-epoch online availability may predate the intent; reports must exceed its baseline. Epoch/revision/baseline ownership remains with the future State/task integration. Descriptor and input validation cannot allocate that context. ACK or valid output never establishes convergence. Even genuine observed agreement is not proof the command caused it.

These metadata policies remain distinct from REQ-015's derived `not_requested`, `unknown`, `pending`, `confirmed` outcomes. No descriptor contains mutable `success`, `ack`, `converged`, runtime status, provider/entity ID or transport address. Completion/deadline evaluation and event correlation are expressly deferred; future dispatch must remain disabled until those prerequisite contracts and governance are reviewed and implemented.

### Strict Boundaries and Diagnostics

External factories revalidate descriptor schemas and payloads, reject unsupported/missing/unknown keys and return immutable typed records with detached JSON snapshots. Invalid validation cannot mutate the input descriptor, catalogue, payload or existing inventory/binding/State. Diagnostics carry deterministic field/index paths and value-free reasons. Arbitrary unknown keys/member names are redacted using established `<unknown>`/`<property>` conventions; no supplied payload, enum constant, description, credentials or underlying exception text is echoed. Individual shape validation makes no Device/provider integrity claim. Catalogue validation additionally enforces pair uniqueness and exact lookup. Neither calls a provider nor consults ambient environment/clock.

## Acceptance Criteria

- [ ] AC1: Version-1 typed descriptors and catalogues validate exact required shapes, ID/revision/text/member constraints and pair uniqueness with detached round trips; malformed/unsupported schema versions, boolean revisions, duplicate keys/pairs, unknown keys and empty-interaction descriptors reject, while sensor-only descriptors, empty collections and coexisting revisions validate and exact lookup never falls back.
- [ ] AC2: Properties/actions/events require their stated schemas and fields; real pure payload validation rejects unknown interactions, undeclared arguments, invalid outputs/events/properties and wrong types without coercion/default values; writable metadata alone grants no write path and unavailable values retain REQ-015 semantics.
- [ ] AC3: Every embedded schema validates the bounded profile, constraints, typed enum uniqueness, required-field references and depth; malformed/inapplicable keywords, remote references, unsupported composition, cyclic input and nonfinite values reject without I/O, while valid nested objects/arrays and parameterless/no-result actions validate.
- [ ] AC4: Every action requires valid risk, bounded integer timeout, idempotency enum and completion-policy object; missing/unknown metadata, false/zero timeout, cross-kind/extra keys and invalid risk/idempotency reject deterministically with no authorization, retry or timer side effect.
- [ ] AC5: Event-confirmed references resolve in the descriptor; state-converged targets resolve only to writable properties and required compatible scalar inputs or valid constants; missing/read-only/unknown references, optional or incompatible inputs and malformed target sources reject. ACK-only metadata remains valid without state/event targets.
- [ ] AC6: Offline fictional evidence distinguishes ACK-only task acceptance from physical convergence: accepted output supplies no State observation; REQ-015 stays unknown/pending after ACK and confirms only on eligible post-baseline matching reports. Uncorrelated events and deadline expiry are documented as insufficient physical evidence, without implementing a task/event/deadline engine.
- [ ] AC7: After requirement approval, independently reviewed required TCs exercise real descriptor/catalogue/schema/payload validators with zero required skips and record tested commit, environment and per-TC executed/skipped results; package lint/type, inventory/binding/State regressions, governance/planning/public-data/legacy gates and installed-wheel smoke pass before runtime acceptance.
