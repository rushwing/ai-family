# REQ-036 — Reconcile canonical state after reconnect

## Admission and authority

[human-001][2026-10-30] Instructed “proceed with hi-s007”. This authorizes
admission and preparation of the bounded HI-S007 specification for review.
Accepted prerequisites are REQ-023 (REST), REQ-028 (event normalization),
REQ-030 (epoch-fenced state application) and REQ-032 (canonical mapping).
This is specification work only: no TC implementation, runtime implementation,
physical-device validation, acceptance or merge is authorized by this record.

## Scope and contract

Add an offline, deterministic reconciliation coordinator in
`home_device_fabric` that combines the existing bounded HA discovery/REST
snapshot and normalized live events with `CurrentStateStore`. The coordinator
is explicitly invoked by its composition owner after a subscription reconnect;
it does not own or alter the WebSocket reconnect lifecycle. It takes validated
canonical inventory, provider bindings and discovery as inputs, and uses the
existing mapper/normalizer and store APIs rather than exposing provider records
to query callers.

For each reconciliation attempt, establish a new monotonically increasing
per-home epoch through the store before applying data. Capture normalized
events observed while obtaining the fresh snapshot into a bounded buffer
associated with that attempt. Apply the complete snapshot as that epoch's
baseline, then apply only buffered events in that epoch whose ordering is
strictly after the snapshot baseline, in deterministic sequence order. Reject
or discard duplicate, older-epoch and at-or-before-baseline events without
regressing reported state. Events arriving after the captured reconciliation
window continue through the normal live event path for the active epoch.

Reconciliation has a finite event-buffer capacity and finite attempt/deadline
limits supplied explicitly at construction. Buffer overflow, invalid or
incomplete discovery, snapshot failure, mapping failure, or store application
failure fails the attempt atomically from the coordinator's perspective: it
must not report successful reconciliation or mark the home fresh. Mark the
home's state stale using the existing store freshness mechanism, retain no
partial success claim, and return a bounded redacted result/error. Retry uses
the existing configured finite reconnect delay/attempt policy; there is no
unbounded loop, implicit sleep beyond the supplied scheduler/clock seam, or
retry after exhaustion. A later explicit successful attempt may restore fresh
state.

The coordinator processes one reconciliation attempt per home at a time.
Concurrent or superseded attempts cannot publish an older snapshot or switch
the active epoch backwards. Inputs and outputs are detached; no raw tokens,
provider mappings, event payload secrets or exception text are included in
diagnostics. The implementation performs no network I/O itself: the caller
supplies the discovery result and coordinates the subscription/event capture.
This keeps transport, authentication and snapshot acquisition in the existing
adapters and makes the state transition testable offline.

## Acceptance criteria

- [ ] AC1: a successful attempt advances the home epoch, applies a complete fresh snapshot, then applies buffered later events in order and reports success only after all writes complete.
- [ ] AC2: events at/before the snapshot baseline, duplicate events, older epochs and superseded snapshots cannot replace newer reported state; events outside the buffer window use the active epoch path.
- [ ] AC3: bounded buffer overflow, invalid/incomplete snapshot, mapper/store failure and exhausted retries leave the home explicitly stale, expose no partial-success result and never exceed configured bounds.
- [ ] AC4: attempts are serialized per home; cancellation, retry scheduling and failure diagnostics are bounded, deterministic under injected clock/scheduler seams and contain no sensitive payloads.
- [ ] AC5: required offline integration/regression tests cover disconnect/reconnect races, repeated reconnect, ordering, failure and isolation; required checks reject skipped or absent runtime gates and record source-specific verification.

## Non-goals

No changes to HA REST/WebSocket protocol or reconnect lifecycle; no transport,
authentication or live HA credentials; no new canonical schema, capability
inference, dynamic inventory policy or durable state store; no action dispatch,
device writes, confirmation/audit changes, HTTP/MCP/UI routes, deployment,
controlled physical-device demo, BUG-033 repair or Feature/Stage acceptance.
The existing event normalizer and state store contracts remain authoritative.
