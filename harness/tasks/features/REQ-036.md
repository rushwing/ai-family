## Scope and contract

Add an offline, deterministic `home_device_fabric` reconciliation coordinator
explicitly invoked by its composition owner after subscription reconnect. It
does not own or alter the WebSocket reconnect lifecycle. The snapshot source is
REQ-031 `HARegistryDiscoveryClient.discover()` and its complete
`HADiscoverySnapshot`; the caller passes its snapshot or fixed discovery
failure code into the attempt. REQ-023 `HARestClient.runtime_info()` provides
version metadata only and is not a state snapshot source. For each attempt,
the composition owner runs the accepted mapper on that same discovery snapshot
and supplies its current bindings, the home's fixed registered inventory,
explicit normalizer profiles from configuration, and already-normalized
buffered live events. The reconciler consumes those outputs; it does not
reimplement registry mapping or live-event normalization. Its only new
projection logic converts discovery state rows to normalized observations and
composes a complete home baseline. It never exposes provider records to query
callers. Mapper output cannot register devices: every mapped device must
already exist in the fixed store inventory, or the attempt fails closed.

### Snapshot projection and atomic publication

For each bound entity, join at most one matching row from discovery `states`
using the provider entity ID in its binding. Duplicate rows for a bound entity
make the snapshot invalid; an unmatched discovery state row is ignored. A
missing row is a no-observation, consistent with REQ-031's permission-filtered
state list, and does not delete the enabled registry entity. Project each
matched row through the
REQ-028 normalizer using its entity profile and the baseline ordering
`{epoch: new_epoch, sequence: 0}`. Each canonical device must have
exactly one selected entity profile, as required by REQ-028; unsupported
multi-entity availability aggregation fails mapping. Build the normalizer input
as `{"event_type":"state_changed","time_fired":row.last_updated,
"data":{"entity_id":binding_entity_id,"old_state":null,
"new_state":row}}`. Use `last_updated` as the
explicit observation timestamp and fail the attempt if it is absent or
invalid. Group resulting per-entity deltas by canonical home/device. The
projection output is exactly one complete canonical DeviceState for every
registered device in the home. An online observation replaces its reported
member and availability; an explicit `unknown` observation writes the
canonical unknown member and unknown availability. An `unavailable` row or a
missing state row sets availability to offline or unknown respectively while
retaining the prior reported member, as required by REQ-028 event semantics.
If a registered device that had a prior binding has no binding in the fresh
mapping, clear its reported-state object and set availability unknown. If a
binding remains but its state row is missing or unavailable, retain its prior
reported member as described above. The projected baseline sets
`desired_state: null`; this satisfies the canonical DeviceState shape but does
not carry intent. The store ignores that submitted field and preserves current
desired intent under its publication lock, so neither a pre-attempt read nor a
concurrent intent update can be overwritten. A device with no prior or projected
observations
has empty reported state and unknown availability; no state or intent is
inferred. Registry devices remain registered through this operation.
The store contract required by this REQ is a home-scoped atomic reconciliation
operation, `reconcile_home(write_context, *, home_id, epoch, baseline_states,
buffered_events, now_ms)`, plus `mark_home_stale(write_context, *, home_id)`.
`write_context` is a trusted exact store context with a configured write grant,
created and held by the composition owner. It is never copied from a query or
tool caller. Reads for `current_states` use this same owner context. The first
operation validates the complete set of registered device states and all
events before publishing anything; it atomically pins the supplied epoch,
rejecting any epoch less than or equal to the current pin or the maximum epoch
floor in stored ordering metadata, with no mutation on rejection,
replaces every registered device's reported state/availability from the
baseline, preserves each current desired intent, then merges buffered events
under REQ-030 ordering. It increments each registered device revision exactly
once, sets its `updated_at_ms` to `now_ms`, and clears the explicit stale
marker as one publication, even when a device's canonical values are
unchanged. A failure changes no states, revisions, freshness or epoch.
This is an explicit REQ-029 store extension; repeated calls are supported and
replace the prior snapshot, including removal of reported members absent from
the new snapshot. It is not REQ-029's one-shot restart `rebuild` or per-device
`put`. The composition owner is the sole trusted writer for the scoped home
and holds an exclusive per-home write barrier for the full retry series: live
events are captured and all other state-store writes are queued until success
or exhaustion. This prevents an uncaptured old-epoch `apply` or `put` from
racing the baseline read/publication. On success, events observed before the
capture window closes join the captured buffer and are published in order.
Events observed after closure remain queued; after atomic publication returns
its epoch, the owner stamps and applies them through the new live path before
reporting reconciliation complete. Queued non-live writes resume after
those events drain. On exhaustion, queued events resume through the still-pinned
old-epoch path and the home remains stale. If a post-closure live apply fails,
the owner marks the home stale and returns failure; the already-published full
baseline remains intact and no reconciliation success is reported. This barrier is
required even though each store operation is internally locked. No partial
state is visible.

### Epochs, buffered events and retry ownership

The composition owner allocates and tracks the next per-home epoch; the store
does not allocate epochs or expose its current pin/floor. For a newly created
in-memory store, the owner starts from unpinned epoch zero and first allocates
one. It retains its highest allocated value for that store's lifetime and
recovers it from owner-owned coordination persistence if the owner restarts
while the store remains alive. If stored states are restored, their saved
ordering and the owner's persisted high-water mark must be restored together;
if the owner cannot prove that its high-water mark is at least the restored
state ordering floor, it fails closed and requires explicit recovery rather
than probing epochs. The owner reserves and persists each new epoch before
starting an attempt, so a crash can skip an epoch but can never reuse one. It
supplies an epoch strictly greater than every previously assigned epoch for
that store. The atomic store operation returns the pinned epoch, which the
owner uses to stamp subsequent live events. A failed attempt may consume its
allocated epoch; it is never reused. This
prevents concurrent or superseded attempts from moving the active epoch
backwards: a stale attempt fails without publication. The composition owner
retains unique buffered events across retry attempts, combines them with
new captures within the same configured capacity, and obtains a fresh discovery
snapshot plus mapper result on each retry. Each attempt allocates a new epoch and increments
`attempt_number`; the finite backoff is applied between attempts. The home
write barrier and bounded capture buffer span the entire retry series. If an
attempt fails and another is allowed, events queued while its atomic store call
was in progress are appended to the pending buffer before the next snapshot;
the combined count remains subject to the configured capacity. On success all
eligible events surviving the timestamp/binding filter below are applied once
in capture order. On terminal failure or
exhaustion, the owner releases the bounded pending queue through the still-
pinned old-epoch path, routes any event rejected due to overflow through that
path after releasing the barrier, keeps the home stale, and returns the
terminal or exhausted result.

Every event captured during the snapshot window is retained with its bounded
capture ordinal in a detached envelope containing the normalized delta, its
source entity ID, original ordering and normalized `observed_at` timestamp.
The source entity ID is retained only inside the trusted coordinator boundary
and is never included in diagnostics. Its incoming ordering belongs to the
pre-reconnect epoch and is not directly applied. After the new baseline is
projected, first deduplicate by source entity ID, original typed delta and
original ordering. Then compare each event with the baseline for that exact
entity: if a matching discovery state row exists, retain the event only when
its normalized `observed_at` is strictly later than that row's normalized
`last_updated`; discard events at or before the baseline timestamp. If the
currently mapped entity has no state row, there is no timestamp baseline and
its buffered events remain eligible. If the event's source entity no longer
maps to the same canonical device, discard it. Assign new sequence numbers
only after deduplication and filtering, in retained capture order: surviving
events receive `(new_epoch, 1..N)` and baseline observations use
`(new_epoch, 0)`. Thus no pre-baseline event can overwrite the snapshot merely
because it was re-based. Events after the capture window are held by the owner
until publication and stamped with the returned epoch and next owner sequence.

Compare timestamps as validated UTC instants using the canonical timestamp
rules, never as raw strings; invalid timestamps fail with `invalid_input`.
Validate that each envelope's entity/profile identifies the normalized delta's
home/device and that `original_ordering` equals the delta's observation
ordering. Re-basing updates ordering on both availability and every reported
member, without changing observation timestamps or values. Filtering is local
to an attempt: the owner retains original envelopes across retries and filters
them again against each fresh snapshot. After publication, the next live
sequence is `N + 1` (one if no buffered event survived).

Each `reconcile(...)` call performs one bounded attempt and no network I/O,
sleep, clock read or retry scheduling. Construction requires a finite positive
buffer capacity and finite input-size bound; overflow is terminal for the
current retry series because retained events cannot fit. The composition owner
enforces a per-attempt deadline: each discovery request is bounded by
`HAConfiguration.request_timeout_ms`, while the
coordinator's projection and publication work is bounded by the explicit input
and event limits. The caller supplies the attempt number and configured
maximum attempt count. Discovery failures, incomplete snapshots and store
publication failures are retryable; invalid input, projection/configuration
errors, epoch conflicts and buffer overflow are terminal. The result exposes
only a finite outcome (`reconciled`, `retryable_failure`, `terminal_failure`
or `exhausted_failure`), the allocated/committed epoch when applicable, and a
fixed failure code. `exhausted_failure` is returned only for a retryable failure
on the last configured attempt. The composition owner applies the existing
`HAConfiguration.reconnect_max_attempts`, `reconnect_initial_delay_ms` and
`reconnect_max_delay_ms` policy, using its own injected scheduler/clock, and
invokes another attempt only within that bound. There is no coordinator
scheduler seam or implicit retry loop. The deadline resets for each fresh
discovery attempt; there is no shared wall-clock deadline. The full retry series
still has a finite upper bound: at most `reconnect_max_attempts` discovery
budgets (including each discovery operation's bounded cleanup allowance) plus
the sum of the configured capped retry delays.

Invalid/incomplete discovery, snapshot failure, projection failure, buffer
overflow or atomic store failure returns failure without publishing a partial
baseline. After a reconciliation attempt has passed authorization, the
coordinator asks the store to mark that home's state explicitly stale on
failure; invalid or unauthorized calls rejected before attempt admission do
not mutate state. This requires the REQ-029 store extension: `read` reports
freshness `stale` for every device in the home while the explicit marker is
set, taking precedence over both uninitialized and TTL-derived freshness.
`mark_home_stale` is idempotent and changes only the home stale marker, not
device revisions or `updated_at_ms`. The attempt result includes
`state_stale: true` only after the marker write succeeds. Existing
TTL freshness alone is insufficient because a failed attempt does not change
`updated_at_ms` or guarantee that TTL has elapsed. A later successful attempt
may restore fresh state.

The composition owner processes one reconciliation attempt per home at a time.
Concurrent or superseded attempts cannot publish an older snapshot or switch
the active epoch backwards. Inputs and outputs are detached; no raw tokens,
provider mappings, event payload secrets or exception text are included in
diagnostics. The implementation performs no network I/O itself: the caller
supplies the discovery result and coordinates the subscription/event capture.
This keeps transport, authentication and snapshot acquisition in the existing
adapters and makes the state transition testable offline.

## Minimum API contract

`ReconnectReconciler(*, store, write_context, registered_inventory,
provider_instance_id, profiles, max_buffer_events, max_input_bytes)` exposes
`reconcile(*, home_id, epoch, attempt_number, max_attempts, discovery_result,
mapping_result, buffered_events, current_states, now_ms)`. `mapping_result`
must be the accepted mapper's output for `discovery_result`; its bindings are
used for this attempt's projection. `registered_inventory` is the fixed
inventory configured in the store and is not replaced by fresh mapper output.
`write_context` is the composition owner's trusted configured write grant
described above. `current_states` is the detached pre-attempt authorized home
snapshot used only to retain old reports for missing or unavailable
observations; it is not the source of desired intent, which the store reads
under its publication lock. `discovery_result` is exactly
`HADiscoverySnapshot` or a finite `HADiscoveryError` from REQ-031.
`mapping_result` is exactly `HAMappingResult` or a finite `HAMappingError` from
REQ-032; it is `None` only when discovery failed and mapping could not run.
These error inputs are trusted typed adapter errors; only their fixed code is
consumed, never exception text. Discovery errors map to `discovery_failed`
(retryable); mapping errors map to `projection_failed` (terminal).
A captured event has exactly `normalized_delta`, `source_entity_id`,
`original_ordering`, `observed_at` and `capture_ordinal`; `observed_at` must
equal the normalized delta's canonical availability observation timestamp.
`current_states` is the detached complete `StateCollection` for every
registered device in the home, ordered by canonical device ID; the owner
collects authorized store `read(...).state` values under the write barrier to
construct it. All integer bounds are exact positive integers;
`1 <= attempt_number <= max_attempts`. It returns a detached result with
`outcome`, `epoch`, `failure_code`, `buffered_event_count`, `state_stale` and
`to_dict()`. `state_stale` is true only when the store stale marker is confirmed.
The finite outcomes are `reconciled`, `retryable_failure`,
`terminal_failure` and `exhausted_failure`; the latter is returned for a
retryable failure when `attempt_number == max_attempts`. Finite failure codes
are `invalid_input`, `discovery_failed`, `incomplete_snapshot`,
`projection_failed`, `buffer_overflow`, `epoch_conflict`, `store_failure` and
`stale_mark_failed`; `mapping_mismatch` reports a mapped device outside the
registered inventory. The store's `epoch_regression` for a non-increasing
candidate maps to `epoch_conflict` in the detached result.
Errors use fixed paths and never retain provider payloads, exception text or
secrets. The composition owner owns event capture, per-home locking, epoch
allocation and retry scheduling. The reconciler performs projection and one
atomic store publication only. On a failed store publication it must complete
`mark_home_stale`; if that operation also fails, it reports
`stale_mark_failed` and does not claim the home is stale.

## Acceptance criteria

- [ ] AC1: a successful attempt advances the home epoch, applies a complete fresh snapshot, then applies buffered later events in order and reports success only after all writes complete.
- [ ] AC2: after source-entity matching, buffered events at or before that entity's snapshot `last_updated` are discarded; only later events are re-based after baseline. Duplicate deliveries, removed bindings, older epochs and superseded snapshots cannot replace newer reported state; events outside the buffer window use the active epoch path.
- [ ] AC3: bounded buffer overflow, invalid/incomplete snapshot, mapper/store failure and exhausted retries leave the home explicitly stale, expose no partial-success result and never exceed configured bounds.
- [ ] AC4: attempts are serialized per home by the composition owner; retry scheduling uses the existing configured finite policy and caller-owned clock/scheduler; failure diagnostics are bounded and redacted.
- [ ] AC5: required offline integration/regression tests cover disconnect/reconnect races, repeated reconnect, ordering, failure and isolation; required checks reject skipped or absent runtime gates and record source-specific verification.

either the current pin or stored floor with zero publication mutation, and
verify that baseline `desired_state: null` preserves current intent. These are
future TC requirements, not claims of implemented or executed runtime tests.
