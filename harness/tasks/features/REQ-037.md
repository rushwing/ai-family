## Contract and scope

Add `home_device_fabric.action_validation.ActionValidator`,
`ActionValidationResult` and `ActionValidationError`.
`ActionValidator(*, registered_inventory, capabilities, max_input_bytes=65536)`
uses one explicit canonical Inventory and a canonical list of device metadata
records with exactly `home_id`, `device_id`, `capabilities`. Each record must
identify an existing device in that inventory and contains a list of accepted
CapabilityDescriptor dictionaries with unique exact ID/version pairs. Reject
unknown scope, duplicate device records, duplicate descriptor pairs, malformed
metadata or provider mapping fields at construction. Metadata is supplied by
trusted composition, not by the action requester. It describes declared support,
not physical availability or permission. Missing device metadata is explicitly
uninitialized; known-empty metadata means no supported capability. Configuration
is detached and immutable; replacement requires a new validator.

`max_input_bytes` must be an exact positive integer at most 16777216. Constructor
inputs and request inputs use the existing bounded plain JSON validation helper
from REQ-032: maximum depth 32, 200000 nodes, bounded scalar/encoded size,
finite numbers, string keys, exact plain JSON types and no cyclic/shared
container references. These fixed structural limits also bound validation
before the configurable request byte limit. Size is UTF-8 bytes of the helper's
canonical JSON encoding, including delimiters and escaping, not transport bytes.
Configuration uses the helper's fixed limits; request size uses those limits
and the configured byte limit. No credentials, provider handles or dispatch
callback are accepted.

The REQ-032 dependency is the package-internal reuse of
`home_device_fabric.ha_mapping._json`. This private helper is not a public export
or a provider-mapping API for action callers. REQ-037 relies on its bounded
plain-JSON validation and canonical encoding described above; changes to that
helper require checking both mapping and action-validation consumers. This
delivery reuses its accepted implementation without changing or promoting it
to a public API.

`validate(request)` accepts raw canonical ActionRequest JSON, never a typed
record that bypasses validation. It returns an immutable result whose
`to_dict()` has exactly `status`, `failure_code`, `request`: status is `valid`
or `rejected`; valid has null failure_code and a detached canonical request,
rejected has a fixed code and null request. A valid result means semantic
validation only. It allocates no task, grants no permission, confirms nothing,
and does not resolve or execute a provider operation. Direct result construction
is internal typed use, not a validation seam. Only validate() supplies checked
results. The caller must apply
trusted identity/policy/confirmation/audit and availability checks separately
before later dispatch. This validator is an internal preflight service, not
an unauthenticated public resource lookup endpoint.

Deterministic validation order and failure codes:

1. Reject non-JSON, cyclic/shared, structurally excessive or malformed canonical
   request shapes as `invalid_request`. A structurally valid JSON encoding over
   `max_input_bytes` returns `input_too_large` before ActionRequest parsing.
2. Parse with the accepted ActionRequest factory, enforcing exact fields,
   identifiers, schema/version types, arguments object and bounded finite JSON.
   Shape/parser failures are `invalid_request`.
3. Wrong canonical home is `unknown_home`; a device not registered in that home
   is `unknown_device` (even if a metadata record once existed elsewhere).
4. Missing metadata for an existing device is `capabilities_uninitialized`.
   Unknown capability ID for that device, including known-empty metadata, is
   `unknown_capability`. A known ID without the requested exact revision is
   `unsupported_capability_version`; never fall back to another revision or
   another device's catalogue.
5. A descriptor with nonempty entirely read-only properties is
   `read_only_capability`, regardless of the requested write action. Otherwise
   an undeclared action is `unknown_action`. No synthesized toggle, sensor
   setter, safety-sensitive action or vendor action is permitted.
6. Validate the declared action's input with CapabilityDescriptor.validate_payload;
   violations (missing/extra fields, types, ranges, enum or schema constraints)
   are `invalid_arguments`. Valid arguments are preserved without conversion,
   rounding, defaulting or mutation.

All rejection codes are finite and contain no submitted values, arbitrary
keys, exception text, provider identifiers or payloads. Construction raises
only fixed `ActionValidationError("invalid_configuration")`, without retaining
an underlying exception chain. Validator/result repr is constant and pickle,
copy and deepcopy are forbidden; `to_dict()` is the supported detached export.
Results expose the full canonical request only on validity to trusted callers;
repr and failure diagnostics never expose it. The validator performs no I/O,
clock/random/environment access, global mutation, retries or provider calls
on either valid or rejected requests. Per-call results and independent validators
remain isolated, including concurrent validation.
