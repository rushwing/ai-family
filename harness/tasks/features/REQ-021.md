## Background

REQ-019 delivers the typed provider boundary and deterministic MockProvider. REQ-020 delivers packaged switch, curtain and read-only temperature models plus an offline CLI. Existing tests exercise these implementations, but no independently callable conformance suite supplies a reviewed inventory that another provider implementation can reuse through the public boundary.

This increment supplies reusable checks and evidence of obligations actually exercised. It contributes HI-S027 to HI-F009; acceptance does not automatically complete HI-F009 or R1, or certify an unimplemented HA adapter.

## Requirement Description

### Reusable Boundary and Packaging

Add conformance support within `toolsets/iot/home-device-fabric` and its existing distribution. A documented public Python entry point accepts an explicitly supplied provider factory/test driver and runs a fixed reviewed inventory. Supply a default offline MockProvider driver for the three packaged fictional models. Construction takes explicit validated fixtures; each case gets a fresh provider and fresh caller State/Task context. Acceptance must exercise an independently supplied forwarding wrapper through the same seam, proving that the runner observes the supplied implementation.

Check logic uses REQ-019 public protocol/records and shared validators, without MockProvider private fields, acceptance-test imports or repository-relative resources. Package reusable logic and fictional stimuli so installed compatible fabric/state-schema wheels can invoke it outside the checkout without pytest. Pytest remains an acceptance/CI dependency. Preserve existing provider/demo exports and behavior. Reviewed TC design freezes exports, driver interface, case IDs, reports and error vocabulary before implementation.

Document separate obligations: provider discovery/snapshot/submission/delivery/settlement; caller validation/State integration/replay policy; deterministic mock scheduling controls. The current protocol includes virtual advancement and mock-specific inputs. Certification covers this offline profile only. A future live adapter needs a controlled driver and reviewed applicability mapping; mandatory cases cannot be silently excluded.

### Independent Stimuli and Expected Results

Reuse validated registrations and packaged models where appropriate. Conformance-owned fixtures explicitly specify reports, availability, virtual times, correlation and expected canonical results. Reports are independent of submitted targets; include a mismatched target fixture. Independently enumerate exact capability ID/revision, units, values, terminal Task state and dispatch counts. Neither the demo's `verified` verdict/expected-task metadata nor a provider verdict serves as the check oracle.

Use actual shared helpers for State/Task projection rather than copying transition, schema, ordering or completion logic. Independent expectations assert their observable effects. Repeated runs use fresh context and produce type-sensitive ordered evidence without ambient timestamps, paths, generated identifiers or environment-derived data.

### Required Check Inventory

| Obligation | Required observable checks |
|---|---|
| Discovery and identity | Discover all three devices with stable canonical home/device IDs, separate bindings and exact revision-1 support. Repeated discovery/fresh construction preserves identity. Mutating exported JSON cannot affect later records. Binding mismatch rejects before effects. |
| Capability validation | Exact-revision descriptor content matches the accepted catalogue, including units/empty events. Switch accepts strict booleans; curtain accepts strict integer 0–100 including endpoints and rejects bool, fractions and out-of-range values. Temperature preserves finite zero/negative/positive Celsius reports and offers no write action. Invalid action/member/revision/payload rejects with fixed typed diagnostics before dispatch. |
| Availability and State | Initial State is unknown. Observations preserve false/zero. Known/unknown offline cases separate availability from last reports. Stale/wrong-epoch evidence cannot replace accepted State or complete a Task. Read-only sensor observations invent no action Task. |
| Action completion | Switch on/off and curtain endpoint/intermediate targets dispatch once. Intermediate/mismatched observations leave the Task running; eligible matching reports complete through shared evidence helpers. ACK alone never establishes success. Scripted failure has unverified physical outcome. Settlement preserves terminal Tasks and suppresses later action outcomes as specified by REQ-019. |
| Deadlines and delivery | ACK-only reaches the existing descriptor deadline. Timeout wins exact ties; late evidence cannot revive timed-out Tasks. A large advance processes earlier eligible evidence before later deadlines. Same-horizon re-advancement repeats no delivery. Times/order are explicit and deterministic. |
| Caller replay/offline policy | Shared scoped type-exact replay classification handles same-request replay and conflicting reuse. Caller suppresses replay/conflict with zero additional dispatches. Offline-before-dispatch rejection is caller policy with zero dispatches, preserving MockProvider.submit behavior. No implicit retry or durable deduplication is claimed. |

Attribute provider-negative and caller-negative checks separately. Caller schema rejection alone does not prove provider rejection of a malformed Task. Exercise provider admission with appropriately constructed invalid submissions and unchanged dispatch evidence, and caller policy through actual shared helpers. Preserve frozen provider error/timeout/settlement and explicit-attempt semantics.

### Reports and Required Acceptance

Return a versioned structured report identifying simulation, offline profile, complete expected case inventory, and one result per case with obligation, executed/pass/fail state and inspectable actual evidence. Missing, duplicate or unexpected IDs cannot produce acceptance success. Account for every mandatory case. Expected device timeout/rejection passes only when independent observations match; failed checks or setup errors fail overall acceptance and cannot produce an empty passing report.

Use stable case IDs and fixed value-free failure diagnostics without arbitrary submitted values or exception chains. Reports contain finite JSON-compatible values and compare exact canonical serialized text, preserving types and list order. Success checks remain effective under Python `-O`. Freeze exact schema/error behavior during TC design.

Add a distinct required-conformance mode at TC design. It fails for absent runner/driver/runtime dependencies, missing inventory, failed checks or any skipped mandatory case. Collection/import failures remain failures. Hermetic gate probes control local present/absent components and prevent fallback to ambient installs. Gate self-tests execute even without the runner/provider. Optional test-first skips are not acceptance evidence.

### Adversarial Proof and Installed Artifacts

The same reusable checks must detect representative defective providers/drivers or isolated mutations: unstable discovery identity/support; ACK incorrectly promoted to success or mismatched evidence accepted; timeout losing an exact tie; same-horizon advancement duplicating a delivery; caller replay/conflict adding dispatch. Alter observable behavior behind the supplied seam or in isolated copies, not expected reports. Each defect fails its corresponding independent check and overall result. A conforming forwarding wrapper passes those same checks. No probes mutate the user's checkout or introduce a second production provider.

Extend the existing offline fabric Python 3.12/3.13/3.14 CI matrix and paired wheel/sdist smoke when implementation is authorized. Changes to checks/drivers/reports must trigger those jobs. Compatible direct-built and sdist-derived wheel pairs execute the complete packaged inventory with `python -I` outside the checkout, repeated exact reports and `-O`. Preserve all existing shared/provider/demo required checks and flags.

## Non-goals

HA/MQTT/Matter/vendor adapters, network, credentials or hardware; new provider semantics/capability revisions/events or unrelated demo scenarios; HTTP/MCP services, UI or R2 workflows; persistent State/Task services, queues, authenticated authorization/confirmation/audit, durable replay/recovery or retries; live certification, production dispatch or Feature/Stage completion. Defects in accepted contracts need explicit BUG/requirement disposition, not silent contract changes.
