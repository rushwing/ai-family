## Requirement Description

Deliver versioned typed State contracts, strict external JSON validation, detached snapshots and pure ordering/convergence evaluation within `libs/state-schema` after requirement review. Use existing package conventions; freeze the public API during reviewed design. No service, state store, adapter or command dispatch is required.

### Version-1 Shape and Identity

State is a separate document, never inventory or ProviderBinding fields. The exact root fields are `schema_version: 1` and `states` (list). Each record has exactly `home_id`, `device_id`, `desired_state`, `reported_state` and `availability`. IDs obey REQ-013 and resolve to the supplied inventory Home and Device. Reject duplicate Device records, cross-home and non-Device references; empty/partial collections are valid. Provider/entity IDs are not canonical state keys. Individual shape validation does not claim reference integrity; collection validation revalidates the inventory without mutation.

State represents named properties, since a Device can report several independent values. Property names match `^[a-z][a-z0-9_]{0,63}$` and denote canonical names, never HA entity IDs, URLs, credentials or actions. This slice defines no capability catalogue, units, writable permissions or vendor conversion. Values are strict JSON scalars: boolean, finite number or string. Reject null, NaN/infinity, lists, objects and coercion; zero and false retain distinct types. Empty strings are valid known scalar values. Property maps may be empty; unknown observations use explicit tags, never magic strings or truthiness.

| Field | Exact shape and meaning |
|---|---|
| `desired_state` | Null when no intent exists; otherwise `{revision, values, report_baseline}`. `revision` is a positive integer intent revision; `values` is a nonempty property-to-scalar map; `report_baseline` is null or `{epoch, sequence}` identifying the accepted reported-stream position when intent was created. It is not an observation. |
| `reported_state` | A property map. Each property is exactly `{status, value, observed_at, ordering}`. `status` is `known` or `unknown`; known requires a scalar value, UTC timestamp and ordering; unknown requires `value: null`, and timestamp/ordering either both null (never observed) or both present (explicit unknown observation). Missing properties are unknown to callers, never default false/zero. |
| `availability` | Exactly `{status, observed_at, ordering}`. Status is `online`, `offline` or `unknown`. Online/offline require timestamp and ordering. Unknown permits both null (unobserved) or both present (explicit unknown event). Availability is independent of property values. |

All listed fields are required, including nullable fields. Unknown structural fields, statuses and unsupported versions fail with deterministic field/index paths and value-free reasons. Boolean values are rejected for integer version/revision/order fields. Input and returned snapshots are isolated; invalid updates cannot alter accepted data. Document any optional normalization; v1 above has no omitted-field defaults.

### Time and Monotonic Ordering

`observed_at` denotes when the adapter/provider actually observed the fact, not command creation, ACK receipt or time of validation. Accepted syntax is `YYYY-MM-DDTHH:MM:SS[.ffffff]Z`, with 1–6 optional fractional digits, a valid UTC calendar instant and no leap seconds. Reject naive/non-UTC timestamps and invalid dates. No ambient wall clock is consulted by validation; observation timestamps may move backwards because clocks change. They are never used to order updates. Age/freshness thresholds, source clock trust and timeout-based offline inference belong to later integrations.

Each `ordering` has exactly `epoch` (nonnegative integer) and `sequence` (nonnegative integer). Compare the pair lexicographically, scoped to one canonical Device's reported stream; property and availability observations share that namespace but each retains its own last accepted pair. Sequence assignment must be monotonic within an epoch, upstream of this pure contract. `epoch` is a canonical ingestion generation, incremented by the future owner on restart, resync or provider replacement; it is not a provider boot ID, timestamp or random UUID. Different Devices and desired revisions are never compared as one stream. Ordering is provided input, not proof of source reliability or persistence.

Specify a pure update decision against an accepted observation and an explicitly supplied current epoch:

- Reject a candidate from an epoch different from the current epoch, including an unestablished future epoch; only the future stream owner may establish a new epoch. Reject invalid types/negative metadata before comparison.
- Within the current epoch, a greater pair replaces that property's/availability's accepted observation, a smaller pair is stale and leaves it unchanged. Equal pairs with identical complete observations are idempotent; equal pairs with different status/value/time are conflicts and fail without mutation.
- On an explicitly established higher epoch, lower-epoch observations are historical and unavailable for current convergence until refreshed. New sequence zero is valid. Reject lowering the current epoch. A delayed old-provider event cannot undo a new generation even if its timestamp or sequence is larger.
- Partial updates affect only named properties or availability; absent members never clear prior observations. Ordering comparisons use the accepted member, not the latest event for another property. A valid newer explicit unknown event supersedes a known value; an older unknown/offline event cannot overwrite a newer member.

The helper has no internal counter, clock, cache or persistence. Caller-supplied current epoch is mandatory context for applying updates and assessing convergence; shape-only snapshot validation cannot assert temporal currency. Desired intent changes use a separate strictly increasing `revision`: equal identical intent is idempotent, equal differing intent conflicts and smaller revision is stale. No ACK changes either stream's revision/order.

### Unknown, Offline and Physical Convergence

Offline means the Device cannot currently be reached; unknown means availability is not established. Neither rewrites last reported values. A known historical `false` or `0` remains preserved with its observation metadata even while offline; it is not a currently usable confirmed reading. Consumers expose availability alongside values and never substitute off/zero for unavailable data. A literal known string `"unknown"` is an ordinary value, distinct from tagged unknown.

The pure convergence result is `not_requested`, `unknown`, `pending` or `confirmed`, derived rather than caller-set. With null desired state return not_requested. Otherwise confirmation requires online availability from the current epoch and known current-epoch reports for every desired property. Each report must have ordering strictly greater than the intent's `report_baseline`; null baseline supplies no causal floor and yields unknown, never confirmed. A baseline from another epoch also yields unknown and requires explicit intent rebasing by its owner under a new desired revision. Ineligible/missing/offline/unknown members yield unknown. Once all evidence is eligible, type-sensitive comparison yields pending for any mismatch and confirmed only when every desired value matches. Numeric integers/floats compare by numeric value; booleans never equal numbers. Extra reported properties do not affect this comparison.

This is observed value agreement after the intent baseline, not proof that the command caused the change. Action/task completion policy, tolerances, units and deadlines are deferred. Retained matching values observed before intent are insufficient. Availability becoming online alone cannot confirm values from a prior epoch or before the baseline.

Provider ACK remains command/task evidence outside State. There is no `ack`, `success` or caller-set `converged` field; attempts to inject them are rejected. An ACK alone cannot set reported values, availability, observed_at or ordering. A future `ack_only` task may finish its own acceptance policy while canonical physical convergence remains unknown/pending; that policy must never fabricate an observation.

## Non-goals

State stores/cache/event bus (HI-S011/012), provider event ingestion/discovery/sync, live HA/mock runtime, action execution/task/idempotency/authorization/audit and completion-policy implementation, capabilities/units/ranges/tolerance, provider source-sequence conversion, persisted epoch allocation, restart coordination, TTL inference, API/UI routes and hardware tests. No inventory/binding schema change, new dependency or external service is required for admission.

## Acceptance Criteria

- [ ] AC1: Strict typed version-1 individual/collection State validation and detached JSON round trips preserve canonical references, desired intent, per-property reports, availability, timestamps and ordering; missing/unknown fields, wrong types, invalid IDs/versions/scalars/timestamps and reference collisions fail deterministically without mutation or private payload exposure.
- [ ] AC2: Known false, integer/float zero and empty string round-trip unchanged and retain their types; explicit unknown, absent property, offline and unknown availability never coerce to those values. Offline retains historical values but cannot yield confirmed convergence.
- [ ] AC3: Ordering tests accept newer members, ignore stale members, allow exact duplicate replay and reject equal-order conflicts; timestamps moving backwards cannot reverse this rule. Partial updates preserve other members, and newer explicit unknown supersedes older known data.
- [ ] AC4: Explicit current-epoch context fences delayed old-provider events and unestablished future epochs; established higher epochs allow sequence reset, invalidate old observations for convergence and never lower generation. Desired revision ordering is independent and follows its stated stale/replay/conflict rules.
- [ ] AC5: Convergence is derived with the documented four outcomes, current online/known evidence, strict post-baseline ordering and type-sensitive value matching. Null/cross-epoch baseline, old matching values, missing properties and offline/unknown evidence cannot confirm. Fresh eligible mismatches are pending; all fresh eligible matches confirm, including false and zero targets.
- [ ] AC6: An acknowledged-only fixture leaves desired intent pending/unknown without inventing reported values, online availability, timestamps or ordering; attempted ACK/success/converged structural fields reject. Later actual observations alone may establish value agreement. ACK-only task success remains distinct from physical convergence.
- [ ] AC7: Independently reviewed required TCs cover AC1–AC6 with real offline validators/helpers, zero required skips, tested commit/environment and per-TC results; package lint/type, inventory/binding regression and governance/public-data/requirements gates pass before runtime acceptance.
