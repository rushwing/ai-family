The six descriptors use `schema_version: 1`, `capability_version: 1` and the exact existing REQ-016 descriptor/envelope fields. Stable IDs and titles are fixed by the table; descriptions are nonblank English text stating the property's meaning, fixed unit and boundaries below. Property/action titles are nonblank descriptive text within REQ-016 limits. Properties have exactly the existing `title`, `description`, `value_schema`, `read_only` fields. Every descriptor has `events: {}`. There is no synthetic change/availability event and no event-confirmed action in this revision.

### Canonical Vocabulary and Value Schemas

The table gives the complete property/action sets; no extra members are allowed in the shipped revision-1 definitions. Schema JSON below is exact: absent keywords stay absent, with no defaults or coercion.

| Title | Stable `capability_id` | Property | Exact `value_schema` | `read_only` | Unit and meaning | Actions |
|---|---|---|---|---|---|---|
| Switchable | `home.switchable` | `is_on` | `{"type":"boolean"}` | false | Boolean on/off state of this control endpoint; true means on. It is not device availability. | `set_on` |
| Positionable | `home.positionable` | `position_percent` | `{"type":"integer","minimum":0,"maximum":100}` | false | Percent of opening: 0 fully closed, 100 fully open; intermediate whole percentages denote the absolute target opening. | `set_position` |
| TemperatureSensor | `home.temperature_sensor` | `temperature_c` | `{"type":"number","minimum":-273.15}` | true | Degrees Celsius; absolute-zero lower bound, no generic upper bound. | none |
| HumiditySensor | `home.humidity_sensor` | `relative_humidity_percent` | `{"type":"number","minimum":0,"maximum":100}` | true | Relative humidity in percent, inclusive 0–100. | none |
| PowerMeter | `home.power_meter` | `power_w` | `{"type":"number"}` | true | Instantaneous active power in watts; positive is consumption/import, negative is generation/export, zero is an observed zero. | none |
| BatteryPowered | `home.battery_powered` | `battery_percent` | `{"type":"number","minimum":0,"maximum":100}` | true | Reported remaining charge percentage, inclusive 0–100; no inferred charging, health or remaining-runtime meaning. | none |

REQ-016 number semantics accept finite integers/floats, excluding booleans; integer accepts only integers, excluding booleans/floats. NaN/infinity and numeric strings reject. Position 50.0 rejects even though mathematically integral. Fractional humidity/battery/temperature/power values are valid within bounds. Do not invent device-specific precision, sensor operating ranges or clamp invalid reports. Electrical energy, current, voltage, charging flags, switch toggle, relative movement, open/close/stop and additional capabilities require later reviewed revisions; none is implicitly supported here. A multi-function Device may eventually expose multiple capability identities, but this slice does not attach or infer them.

Units and direction are normative meanings of the exact `(capability_id, capability_version, property)` tuple and are repeated in property descriptions. They are not parsed from arbitrary human text. There is no `unit` descriptor field or JSON Schema keyword: REQ-016's strict profile stays unchanged. Clients/adapters must deliberately implement this known revision's meaning, never infer units or compatibility merely from structural validation of a foreign descriptor. A generic unit-metadata API or schema-profile extension requires a separately reviewed contract. Changing unit, direction, property type, range, action schema or metadata requires a new capability revision; exact lookup never falls back to latest.

### Writable Actions and Completion Metadata

Each action input is an exact closed object schema with the single required member below. `additionalProperties` is literal false; missing keys or additional arguments reject. The input member's scalar schema is structurally identical to the target property schema, including bounds, satisfying REQ-016's state-converged reference rule.

| Capability action | Exact `input_schema` | `output_schema` | `risk` | `timeout_ms` | `idempotency` | Exact `completion_policy` |
|---|---|---|---|---|---|---|
| Switchable `set_on` | `{"type":"object","properties":{"is_on":{"type":"boolean"}},"required":["is_on"],"additionalProperties":false}` | `{"type":"null"}` | `medium` | 30000 | `safe_repeat` | `{"kind":"state_converged","targets":{"is_on":{"source":"input","field":"is_on"}}}` |
| Positionable `set_position` | `{"type":"object","properties":{"position_percent":{"type":"integer","minimum":0,"maximum":100}},"required":["position_percent"],"additionalProperties":false}` | `{"type":"null"}` | `medium` | 120000 | `safe_repeat` | `{"kind":"state_converged","targets":{"position_percent":{"source":"input","field":"position_percent"}}}` |

Null output denotes no result payload; validation of null is not provider acceptance or task success. A later provider/task envelope may carry ACK independently, as reviewed under HI-S019. No `{accepted:true}` object is accepted as these actions' output. Setting an absolute boolean/position is repeat-safe at the intent level; this is not a retry/deduplication guarantee. Timeouts begin at future governed dispatch, excluding queue/admission time, as REQ-016 specifies; expiry cannot establish physical failure or rollback. These defaults are exact revision-1 declarations, not authorization or promises every provider/device meets them. Later trusted policy may raise risk, require confirmation or deny (including a switch attached to dangerous equipment); it cannot lower risk by editing the descriptor or bypass scope/role/confirmation/audit.

Position convergence uses REQ-015's exact type-sensitive agreement with the requested whole percentage; no epsilon, rounding, deadband or partial-position completion is added. A provider that cannot supply the canonical integer observation or meet this evidence contract must not be advertised as supporting this revision. The current offline catalogue implements no provider suitability check or physical task engine. The two actions remain unavailable for execution until task/adapter/governance prerequisites are separately reviewed and implemented.

### Measurements, Availability and State Boundary

All four sensor descriptors have exactly one read-only property, `actions: {}` and `events: {}`. They expose no set/reset/calibrate action, writable target or inferred threshold event. Unknown actions reject through actual REQ-016 selection, including `set_on` on any sensor.

REQ-015 State metadata represents absence, unknown and offline outside property payloads; REQ-017 adds no availability field to the Capability descriptor or value schema. A scalar property validation accepts known canonical values only. Null, `unknown`, `unavailable`, missing-value substitutions and false/zero fallbacks reject as measurement payloads. Legitimate zero/false readings remain valid and distinct from missing reports. Validating a reading never updates State, availability, ordering, timestamps or desired intent. A stale last-known value during offline availability cannot prove current physical state or completion.

Provider unit conversion, Fahrenheit conversion, energy-to-power derivation, reverse position scales and precision normalization belong to later adapters. They must occur before canonical payload validation and preserve provenance under reviewed contracts. This catalogue does not perform conversions or silently infer a device's units from its name/provider data. No State/store/provider integration is delivered.

### Catalogue Integrity and Isolation

Use the REQ-016 envelope `{schema_version: 1, capabilities: [...]}` with exactly the six pairs in table order. Each shipped definition must pass `CapabilityDescriptor`/`CapabilityCatalogue` validation and duplicate-key-safe text ingestion. This is a closed initial catalogue, not a restriction on REQ-016's general-purpose validator, which continues to accept other structurally valid IDs/revisions. Unknown lookup or any version other than 1 fails exact selection; it cannot synthesize a descriptor or upgrade/downgrade.

The accessor returns independently validated immutable records with detached JSON snapshots. Mutating an exported dictionary/list cannot change a record or future catalogue retrieval. No shared mutable source object or Device attachment is exposed. Invalid property/action/input/output/member selections use existing deterministic value-free `CapabilityError` diagnostics; do not log submitted values or underlying exceptions. The future implementation must fail closed on a malformed packaged catalogue rather than bypass validation or repair it silently. No new generic Capability schema keywords, errors or validation semantics are introduced.
