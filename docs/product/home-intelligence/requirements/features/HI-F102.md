# HI-F102 — Workflow Persistence

## Outcome

A workflow resumes from durable state after process restart without repeating completed physical actions.

## User / System Value

A workflow resumes from durable state after process restart without repeating completed physical actions. This capability is independently demonstrable through the scenario below.

## Scope

- Persist run identity, step state, waits, timeout deadlines and tenant scope.
- Reuse LangGraph/PostgreSQL patterns only after verifying their production runtime gaps.
- Resume reconciles business state and task outcomes; retries preserve idempotency.

## Non-goals

A second orchestration engine or broker-owned workflow state.

## Architecture Boundaries

Inherit [architecture alignment](../../ARCHITECTURE_ALIGNMENT.md), ADR-016 and ADR-010. Provider identifiers stay in adapters and ProviderBinding; device writes remain governed asynchronous tasks.

## Acceptance Criteria

- [ ] Persist run identity, step state, waits, timeout deadlines and tenant scope.
- [ ] Reuse LangGraph/PostgreSQL patterns only after verifying their production runtime gaps.
- [ ] Resume reconciles business state and task outcomes; retries preserve idempotency.

## Dependencies

- [HI-F101](HI-F101.md)

## Stories

No stories are created for R2. Refine only when this stage becomes active.

## Demo Scenario

Stop a mock run after an action, restart and observe one recorded action.

## Risks / Open Questions

Provider support and physical completion must be demonstrated, not inferred from an ACK. See the source crosswalk and current-state evidence. No story is marked complete from prototype UI alone.
