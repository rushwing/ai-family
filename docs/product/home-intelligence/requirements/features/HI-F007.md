# HI-F007 — Capability Execution API

## Outcome

An authorized typed capability request executes through the appropriate provider binding.

## User / System Value

An authorized typed capability request executes through the appropriate provider binding. This capability is independently demonstrable through the scenario below.

## Scope

- Requests use canonical device/capability/action IDs with validated parameters and idempotency keys.
- Only registered mappings may resolve a request into a provider operation.
- Device writes use asynchronous task semantics; accepted/transport ACK is distinct from reported physical completion.

## Non-goals

Direct HA calls from workflows or agents; arbitrary service or MQTT execution.

## Architecture Boundaries

Inherit [architecture alignment](../../ARCHITECTURE_ALIGNMENT.md), ADR-016 and ADR-010. Provider identifiers stay in adapters and ProviderBinding; device writes remain governed asynchronous tasks.

## Acceptance Criteria

- [ ] Requests use canonical device/capability/action IDs with validated parameters and idempotency keys.
- [ ] Only registered mappings may resolve a request into a provider operation.
- [ ] Device writes use asynchronous task semantics; accepted/transport ACK is distinct from reported physical completion.

## Demo Scenario

Submit a confirmed switch or curtain task, show accepted first and then its policy-defined terminal result.

## Risks / Open Questions

Provider support and physical completion must be demonstrated, not inferred from an ACK. See the source crosswalk and current-state evidence. No story is marked complete from prototype UI alone.
